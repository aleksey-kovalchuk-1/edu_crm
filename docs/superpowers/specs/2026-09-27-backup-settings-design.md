# Настройки → Резервное копирование

Срез 5 из 5 запроса «Настройки» от 27.09.2026. Согласовано с владельцем 27.09.2026: только `crm-superadmin`; ручная копия — через флаг запроса и отдельный агент на Mac; восстановления и удаления в этой задаче нет.

## Источник данных: отчёт настоящего механизма

Копии делает `scripts/scheduled-backup.sh` на Mac (LaunchAgent `tech.unicrm.backup`, ежедневно в 03:30) в закрытый `BACKUP_DIR` вне репозитория. Контейнер API этот каталог не видит и запускать скрипты на Mac не может — и не должен.

- После каждого запуска (успех или ошибка) `scheduled-backup.sh` вызывает `scripts/backup_status.py`, который атомарно пишет `status.json` в `BACKUP_STATUS_DIR` (по умолчанию `deploy/local/backup-status`, каталог вне Git):
  `{"schema": 1, "updated_at", "last_run": {"trigger": "scheduled"|"manual", "label", "started_at", "finished_at", "result": "running"|"success"|"failure", "verified": true|false|null, "error": "<короткий код>"|null}, "last_success_at", "pairs": [{"label", "database": {"file", "size_bytes", "created_at"}|null, "attachments": {...}|null}], "retention": {"days", "min_pairs", "verification_configured"}}`.
- В отчёте только имена файлов, размеры и даты — без путей, ключей, адресатов `age` и содержимого. Пары — по метке, новые сверху, не больше 60.
- В начале запуска пишется `result: "running"`; ловушка `EXIT` записывает итог.
- Каталог монтируется в `api` **только для чтения** (`/data/backup-status`).

## Ручная копия

- `POST /api/v1/backups/manual` (только `crm-superadmin`) создаёт файл-флаг `request.json` (`{"requested_at", "requested_by_user_id"}`) в `BACKUP_REQUEST_DIR` (по умолчанию `deploy/local/backup-requests`, в `api` — `/data/backup-requests`, запись разрешена только в этот каталог). Если запрос уже ждёт или копия выполняется — `409`. Событие журнала `backup.manual_requested`.
- LaunchAgent `tech.unicrm.backup-request` (`WatchPaths` на каталог запросов) запускает `scripts/run-requested-backup.sh`: переименовывает флаг (атомарно, повтор не запускает вторую копию), запускает **тот же** `scheduled-backup.sh` с меткой `manual-<UTC>` и `BACKUP_TRIGGER=manual`, удаляет флаг. Содержимое флага, кроме числового id, не используется — никаких параметров из контейнера.
- Ручные копии не удаляются автоматически (правило хранения удаляет только ежедневные пары).
- Контейнер не получает Docker, сокетов и доступа к Mac.

## API и интерфейс

- `GET /api/v1/backups/status` (только `crm-superadmin`) → `{"available", "reason", "last_run", "last_success_at", "stale", "pairs", "retention", "pending_request"}`. Нет отчёта — `available: false`, «Отчёт о резервном копировании пока не записан: служба копирования ещё не запускалась с этой версией». Повреждённый отчёт — «Отчёт о резервном копировании повреждён». `stale: true`, если последняя успешная копия старше 36 часов или её нет.
- Прямой выдачи файлов копий нет; восстановления и удаления нет.
- «Настройки → Резервное копирование»: последний запуск (время, способ, результат, проверка расшифровкой), предупреждение о давности, список пар с размерами и датами, срок хранения, кнопка «Создать копию сейчас» с состояниями «Запрошена → Выполняется → Готово/Ошибка» (опрос раз в 10 секунд, пока запрос ждёт или копия выполняется).

## Проверка

Скрипты: `backup_status.py` — пары, отсутствие путей, running/success/failure; `run-requested-backup.sh` — один запуск на флаг, метка `manual-…`, повторный вызов без флага ничего не делает (с поддельным `scheduled-backup.sh`). Бэкенд: роли (`crm-admin` — 403), отчёт нет / повреждён / устарел / в порядке, запрос создаётся, `409` при ожидающем запросе и при выполнении, в ответах нет путей. Фронтенд: состояния страницы и кнопки.

## Выпуск (с разрешения владельца)

Создать каталоги `deploy/local/backup-status` и `deploy/local/backup-requests`, пересоздать `api` с новыми томами, установить второй plist, один раз запустить `scheduled-backup.sh`, чтобы появился отчёт.
