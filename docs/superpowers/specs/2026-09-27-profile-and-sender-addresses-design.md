# Личный профиль и адреса отправителей

## Решение и границы

«Настройки → Личный профиль» становится редактируемой анкетой: имя, фамилия, телефон, часовой пояс, аккаунты в мессенджерах и адрес, от которого уходят письма вузам. SMS-подтверждение телефона убирается; подтверждается только адрес электронной почты отправителя — после одобрения руководителем или администратором.

Регистрация новых пользователей не меняется: её ведёт отдельная работа (см. «Основа»). Отображение времени в выбранном часовом поясе по всему приложению, интеграции с мессенджерами и отправка реальных писем без настроенного почтового провайдера в эту работу не входят.

Согласовано с владельцем 27.09.2026: одобряет адрес отправителя; имя хранится в Keycloak; одобряют `crm-supervisor` или `crm-admin`; подтверждённый адрес принадлежит только заявителю.

## Основа: ветка GPT

Параллельно в рабочем дереве `codex/customer-data` (на 27.09.2026 изменения не закоммичены) GPT меняет создание учётных записей, Keycloak и права менеджеров: миграция `0024_team_visible_universities`, в `backend/app/keycloak_admin.py` — `create_user`, `set_user_enabled`, `delete_user`, `KeycloakAdminConflict`, поля `AdminUser.first_name/last_name/enabled`.

- Ветка реализации создаётся от завершённой и закоммиченной ветки GPT, не от `ai/design-tokens`. До этого реализация не начинается.
- Миграция этой работы — `0025`, `down_revision = '0024'`. Если номер у GPT изменится, `down_revision` меняется вслед за ним.
- Обновление имени добавляется в `KeycloakAdminClient` рядом с `set_user_enabled` и использует `AdminUser.first_name/last_name`. Метод сначала читает представление пользователя (`GET /users/{id}`), меняет `firstName`/`lastName` и отправляет его целиком (`PUT`), чтобы проверка пользовательского профиля Keycloak не отбросила остальные атрибуты.
- Рабочая система обновляется только после выпуска ветки GPT; порядок выпуска: ветка GPT → эта работа.

## 1. Профиль

### Поля

| Поле | Хранение | Правила |
| --- | --- | --- |
| Имя, фамилия | Keycloak (`firstName`/`lastName`) + зеркало `users.first_name`/`users.last_name` | 1–100 символов каждое после обрезки пробелов; `full_name = "<имя> <фамилия>"`, не длиннее 200 |
| Email | Keycloak, только чтение | Не редактируется в CRM |
| Телефон | `users.phone` (существующее поле) | Необязательный; нормализуется существующим `app/phone.py::normalize_phone`; без подтверждения |
| Часовой пояс | `users.timezone`, `varchar(64)`, по умолчанию `Europe/Moscow` | Проверка через `zoneinfo.ZoneInfo`; во фронтенде — список с поиском из `Intl.supportedValuesOf('timeZone')` |
| Мессенджеры | `users.messengers`, JSONB, по умолчанию `[]` | Список `{service, handle}`; `service` ∈ `telegram`, `whatsapp`, `viber`, `vk`, `max`, `other`; `handle` 1–100 символов, ведущий `@` обрезается; не более 10 записей |
| Адрес отправителя | `users.email_sender_identity_id` (существующее поле) | См. раздел 2 |

### API

- `GET /api/v1/profile` — профиль текущего пользователя.
- `PATCH /api/v1/profile` — частичное обновление текущего пользователя; идентификатор пользователя не передаётся.
- `/auth/me` дополнительно отдаёт `first_name`, `last_name`, `timezone`, `messengers`; `phone_verified_at` из ответа убирается.

Порядок сохранения в `PATCH`: проверка всех полей → если имя изменилось, проверка уникальности нового `full_name` (раздел 1.2) → вызов Keycloak → запись локальных полей и каскад переименования (раздел 1.2) → журнал → один `commit`. Keycloak вызывается, только если имя действительно изменилось. Если клиент администрирования Keycloak не настроен или Keycloak ответил ошибкой, запрос завершается `503` с понятным сообщением, и ничего из запроса не сохраняется. Изменения остальных полей в журнал пишутся без значений телефона и мессенджеров (только названия изменённых полей).

### Синхронизация при входе

`Identity` получает `given_name` и `family_name` из токена. Оба пути синхронизации — upsert в обработчике входа (`auth.py`, callback) и повторная проверка сессии (`auth.py`, revalidation) — перестают писать `full_name` напрямую и вызывают общую функцию `apply_full_name(db, user, first_name, last_name, full_name)`, которая обновляет поля и запускает каскад, если имя изменилось. Для upsert прежнее имя читается до вставки. Поскольку CRM пишет имя в Keycloak, следующий вход приносит то же имя, и правка не затирается.

### 1.1. Удаление подтверждения телефона

Удаляются: эндпоинты `POST /api/v1/profile/phone` и `/phone/verify`, хуки подтверждения в `frontend/src/api/profile.ts`, пошаговый интерфейс кода и баннер «Вы не до конца прошли регистрацию» в `SettingsProfilePage.tsx`.

Не изменяются: `app/phone.py` (используется для нормализации телефона профиля), `app/sms.py`, телефоны контактов вузов, вендоров и слушателей (`models.py`, отдельные столбцы), `catalog_routes.py`, `customer_imports.py`, `learner_routes.py`, `vendor_routes.py`, импорт компаний и слушателей. Существующие значения `users.phone` сохраняются. Таблица `phone_verification_codes` и столбец `users.phone_verified_at` остаются в схеме без использования: удаление данных необратимо и не требуется для задачи.

### 1.2. Правило смены ФИО

**Проблема.** `Launch.owner` — ответственный по взаимодействию, свободный текст `varchar(100)`. От совпадения этого текста с `User.full_name` зависят:

- автоназначение шага `interaction_owner` (`plan_routes.py::resolve_assignee`: `lower(trim(User.full_name)) == lower(trim(launch.owner))`) — после переименования совпадения нет, и шаг получает «Не удалось однозначно сопоставить ответственного»;
- фильтр отчёта (`report_routes.py`: варианты — `DISTINCT Launch.owner`, отбор — `Launch.owner IN (...)`) — старые взаимодействия остались бы под старым именем, новые под новым, и один человек превратился бы в два значения фильтра.

**Правило.**

1. Миграция `0025` добавляет `launches.owner_user_id` (nullable FK на `users.id`, индекс) и расширяет `launches.owner` до 200 символов, чтобы вместить `full_name`. Схема `LaunchInput.owner` расширяется до 200.
2. Заполнение при миграции: взаимодействие связывается с пользователем, только если ровно один активный пользователь имеет совпадающее по `lower(trim(...))` имя. Неоднозначные и несовпавшие строки остаются без связи, их текст не меняется.
3. Функция `match_owner_user(db, owner_text)` реализует то же правило. Создание и изменение взаимодействия вызывают её и устанавливают или очищают `owner_user_id`. Поле формы остаётся текстовым.
4. `resolve_assignee` для `interaction_owner`: если `owner_user_id` указан и пользователь активен — назначается он; иначе прежнее текстовое сопоставление.
5. **Каскад.** Когда `full_name` пользователя меняется (профиль или синхронизация при входе), в той же транзакции выполняется `UPDATE launches SET owner = :new WHERE owner_user_id = :user_id` и пишется событие `user.renamed` с прежним и новым именем и числом обновлённых взаимодействий. Строки без связи не изменяются никогда.
6. Код отчёта не меняется. Связанные строки несут новое имя, поэтому в фильтре один вариант на человека, и отбор по нему возвращает его взаимодействия до и после переименования.
7. Через профиль нельзя взять имя, которое уже есть у другого активного пользователя (`lower(trim(full_name))`): ответ `422` с полем `first_name`. При синхронизации из Keycloak отказ невозможен — каскад выполняется, а совпадение пишется в журнал приложения как предупреждение; связанные строки продолжают работать по `owner_user_id`.
8. Ошибка Keycloak при сохранении профиля: локальное имя, связанные взаимодействия и журнал не меняются.

**Регрессионные тесты** (backend):

- переименование через профиль → генерация плана назначает шаг `interaction_owner` тому же пользователю по взаимодействию, созданному до переименования;
- `/reports/options` после переименования содержит новое имя и не содержит старое; отчёт с фильтром по новому имени возвращает взаимодействие, созданное до переименования;
- переименование через синхронизацию при входе (изменённый `name`/`given_name`/`family_name` в токене фейкового Keycloak) выполняет тот же каскад; то же для повторной проверки сессии;
- взаимодействие без связи, чей текст не совпадает ни с кем, и неоднозначное взаимодействие не изменяются;
- заполнение миграции: единственное совпадение связывается, два одноимённых пользователя и отсутствие совпадения — нет;
- новое взаимодействие, набранное с новым именем, связывается с пользователем;
- ошибка Keycloak оставляет имя, взаимодействия и журнал без изменений;
- имя другого активного пользователя отклоняется с `422`.

## 2. Адреса отправителей

### Данные

Миграция `0025` добавляет в `email_sender_identities`:

| Столбец | Назначение |
| --- | --- |
| `owner_user_id` | FK на `users.id`; `NULL` — общий адрес |
| `status` | `pending_approval`, `awaiting_confirmation`, `active`, `rejected`; CHECK-ограничение |
| `requested_by_user_id`, `requested_at` | Кто и когда подал заявку |
| `approved_by_user_id`, `approved_at` | Кто и когда одобрил |
| `rejection_reason` | До 500 символов |
| `confirmation_token_hash`, `confirmation_expires_at`, `confirmation_sent_at` | Одноразовая ссылка подтверждения; хранится только хеш (`security.token_hash`) |
| `confirmed_at` | Когда адрес подтверждён |

**Сохранение существующего.** Все существующие строки получают `owner_user_id = NULL`, `status = 'active'`, их `is_active` не меняется. `users.email_sender_identity_id` не изменяется ни у одного пользователя. Уникальность `email_address` остаётся глобальной; повторная заявка на отклонённый адрес переиспользует строку (как нынешнее восстановление деактивированного адреса).

### Процесс

1. **Заявка.** Пользователь в профиле вводит адрес и отображаемое имя → строка `pending_approval` с `owner_user_id` = заявитель. Одновременно у пользователя может быть одна открытая заявка (`pending_approval` или `awaiting_confirmation`); отозвать её может сам заявитель. Адрес, уже занятый активной или открытой строкой, отклоняется.
2. **Одобрение.** `crm-supervisor` или `crm-admin` видит очередь в «Настройки → Организация» (сейчас заглушка; остальным ролям страница показывает прежний текст). Одобрить или отклонить с причиной. Одобрить собственную заявку нельзя (`403`).
3. **Письмо подтверждения.** Одобрение переводит строку в `awaiting_confirmation`, создаёт токен (`secrets.token_urlsafe`), действующий 48 часов, и отправляет на заявленный адрес ссылку `/confirm-sender?token=…` от системного отправителя (`settings.email_sender_address`). Повторная отправка — действием администратора, не чаще раза в 60 секунд; новая ссылка аннулирует прежнюю.
4. **Подтверждение.** Ссылка открывает публичную страницу вне `AuthGate` с кнопкой «Подтвердить». Кнопка отправляет `POST /api/v1/email-senders/confirm` с токеном; запрос с `GET` ничего не подтверждает, чтобы почтовые сканеры, открывающие ссылки заранее, не подтверждали адрес. Эндпоинт не требует сессии (владение ящиком доказывает токен) и поэтому не использует CSRF-проверку сессии. Токен одноразовый; просроченный, повторный или неверный токен даёт одинаковый ответ «Ссылка недействительна или устарела». После подтверждения: `status = 'active'`, токен стирается, адрес становится выбранным в профиле владельца.
5. **Общие адреса.** Администратор добавляет общий адрес (`owner_user_id = NULL`) без шага заявки, но строка создаётся в `awaiting_confirmation`, и на адрес уходит письмо подтверждения.
6. **Без почтового провайдера.** Если `settings.email_provider_url` не задан, письмо только записывается в журнал сервера, и ответ одобрения или повторной отправки прямо говорит об этом — по существующему правилу `email_routes.test_send`.

Каждый переход пишется в журнал действий (`email_sender.request`, `.withdraw`, `.approve`, `.reject`, `.confirmation_resent`, `.confirm`) без токена.

### Проверка непосредственно перед отправкой

Единая функция `usable_sender(db, user, identity_id) -> EmailSenderIdentity` перечитывает строку свежим запросом (`populate_existing`, `FOR SHARE`) и требует одновременно: `is_active`, `status = 'active'`, `owner_user_id IS NULL` или `= user.id`. Иначе — `AppError(CONFLICT, 'Выбранный адрес отправителя недоступен — выберите другой в профиле')`.

- Вызывается непосредственно перед каждым вызовом отправителя письма, в том числе в `POST /email-senders/test`; при отказе письмо не отправляется и тихой подмены на системный адрес нет. Если адрес не выбран, как и сейчас используется системный отправитель.
- Выбор адреса в `PATCH /api/v1/profile` проверяется той же функцией.
- Выбор, ставший недоступным позже (адрес деактивирован), сохраняется в `users.email_sender_identity_id`, а профиль показывает его как недоступный.
- Это исправляет текущую ошибку: `test_send` сейчас использует выбранный адрес без проверки `is_active`.

Список `GET /api/v1/email-senders` для обычного пользователя возвращает только активные общие адреса и его собственные адреса (со статусами); очередь заявок доступна только руководителю и администратору.

### Тесты

- миграция сохраняет существующие строки активными и общими, выбор пользователей не меняется;
- гонка: адрес выбран, затем деактивирован → тестовое письмо отклоняется, отправитель не вызывается;
- чужой личный адрес, адрес в `pending_approval`, `awaiting_confirmation` и `rejected` отклоняются и при выборе, и при отправке;
- просроченный, повторно использованный и неверный токены отклоняются; `GET` не подтверждает;
- одобрение собственной заявки — `403`; вторая открытая заявка отклоняется; пользователь без роли руководителя/администратора не видит очередь;
- повторная отправка чаще раза в 60 секунд отклоняется, новая ссылка аннулирует прежнюю;
- без провайдера ответ одобрения сообщает, что письмо только записано в журнал;
- подтверждение делает адрес выбранным у владельца.

## 3. Интерфейс

- **Личный профиль:** панель «Личные данные» (имя, фамилия, email только для чтения, телефон, часовой пояс), панель «Мессенджеры» (добавить, изменить, удалить строку), панель «Адрес отправителя» (выбор из доступных; своя заявка со статусом и причиной отказа; форма новой заявки; отзыв; тестовое письмо).
- **Организация:** для руководителя и администратора — «Заявки на адреса отправителей» (одобрить, отклонить с причиной, повторить письмо) и «Общие адреса» (добавить, деактивировать).
- **Публичная страница** `/confirm-sender` — кнопка подтверждения и результат.
- Фронтенд-тесты: сохранение полей профиля, ошибка Keycloak показывается и форма остаётся заполненной, баннера о телефоне нет, выбор недоступного адреса отображается как недоступный, очередь видна только нужным ролям, страница подтверждения не подтверждает без нажатия.

## 4. Проверка перед выпуском

- Полные наборы backend- и frontend-тестов проходят, включая существующие тесты импорта и контактов без изменений.
- Миграция `0025` применяется поверх `0024` на копии рабочей БД; число строк `email_sender_identities` и значения `users.email_sender_identity_id` до и после совпадают; отчёт о связанных/несвязанных взаимодействиях после заполнения показан владельцу.
- Документация API (`docs/api/`) и `docs/decisions.md` обновлены: отмена SMS-подтверждения телефона (D-155–D-157), новое правило адресов отправителей вместо «только каталог администратора».
