# Работа с файлами: план для генерического импорта XLSX и загрузки PDF/DOCX

Источники: `RTK_IT_School_CRM_MVP1_Product_Brief_EN.docx` (продуктовый бриф, версия 1.1, 2026-09-16) и
`AI_TASK_Operational_CRM_File_Ingestion.md` (техническое задание). Это план, а не код — перед реализацией
нужно подтверждение решений в разделе «Решения, требующие подтверждения владельца» ниже.

## 0. Как читать этот документ

Бриф называет роли `KAM` / `Manager` / `Platform administrator` и потоки «Excel-импорт» и «загрузка
PDF/DOCX» на верхнем уровне продукта. В этом репозитории те же роли уже существуют как `crm-user` /
`crm-supervisor` / `crm-admin` (Keycloak), и часть Excel-импорта уже реализована (T-033). План ниже —
это то, что нужно **добавить и переделать** поверх существующего кода, а не с нуля.

### 1.3 Модель сущностей — что реально можно импортировать

В брифе перечислены «universities, contacts, programs, products, contracts, interactions», но в этой
схеме БД нет отдельной модели «Program» (`program` — строковое поле на `Launch`, т.е. «взаимодействии»).
Сам бриф рекомендует (раздел 10, «Initial target entities»): **начать с universities, contacts и
interactions; contracts — после подтверждения полевой модели**. План следует этой рекомендации:

- Фаза 0A, первая волна импорта: **университеты** (`University`), **контакты вуза**
  (`UniversityContact`), **взаимодействия** (`Launch`, создание новых записей — обновление статуса через
  импорт не предусмотрено, это отдельный процесс, workflow).
- Существующий импорт договоров (T-033) остаётся как есть — он уже реализован и не входит в объём этой
  задачи; просто попадает в тот же обобщённый реестр импортёров, если время позволит без риска регрессии.
- Отдельная сущность «Program» и «Product» как объекты импорта — вне рамок Фазы 0 (нет модели / уже
  импортируются как часть договоров).

## 2. Роли и права — сопоставление с бригад-моделью брифа

| Бриф | В этом проекте | Права на импорт/загрузку (предлагается) |
|---|---|---|
| KAM | `crm-user` | Импорт и загрузка только в рамках назначенных вузов (существующий скоуп, `university_scope`) |
| Manager | `crm-supervisor` | Видит и может проверять импорты всей команды (все вузы), может отклонить/переназначить |
| Platform administrator | `crm-admin` | Настраивает политики (форматы, лимиты, retention); **не получает доступ к содержимому бизнес-документов по умолчанию** — это принципиально новое ограничение, которого сейчас нет (`crm-admin` сейчас видит всё) |

Пункт «Platform administrator boundaries» / «break-glass access» из брифа (раздел 2.1) — это отдельная,
более крупная работа над моделью доступа (в брифе она прямо отнесена к «Phase 1: role and access
hardening», не к Phase 0). **В объём этой задачи не включаем**: `crm-admin` в Фазе 0 сохраняет
существующий полный доступ (как сейчас, D-102/D-128), но каждое обращение администратора к содержимому
документа отдельно попадает в аудит, чтобы Phase 1 могла добавить ограничение без переделки модели данных.
Явно фиксируем это как допущение — см. раздел 6.

## 3. Архитектура

### 3.1 Обобщённый импорт по сущности

Реестр импортёров вместо одного захардкоженного потока:

```python
IMPORTERS: dict[str, EntityImporter] = {
    'universities': UniversityImporter(),
    'university_contacts': UniversityContactImporter(),
    'interactions': LaunchImporter(),
    # 'contracts': existing ContractImporter() — обёртка над уже работающим кодом T-033
}
```

Каждый `EntityImporter` предоставляет: список полей (с синонимами заголовков — переиспользуем
`FIELDS`/`suggest_mapping` из `importer.py`), функцию построчной валидации (обязательные поля, типы,
ссылочные значения, скоуп пользователя, дубликаты/идентичность строки), функцию записи (create/update).
`POST /api/v1/imports` получает новый обязательный параметр `entity`; шаги upload → check → apply не
меняются на уровне API, меняется то, что внутри `check`/`apply` вызывается импортёр по `entity`.

### 3.2 Фоновые задачи (используется и для отчётов позже, D-109)

Новая таблица `background_jobs` (`id`, `kind`, `status` [`queued`/`running`/`succeeded`/`failed`],
`payload` JSON, `result` JSON, `correlation_id`, `created_by_user_id`, `created_at`, `started_at`,
`finished_at`). Новый контейнер-воркер в `compose.yaml` (тот же образ API, другая команда: цикл
`SELECT ... FOR UPDATE SKIP LOCKED` по `background_jobs` — без Redis, без Celery, консистентно с D-109).

`POST /imports/{id}/apply` перестаёт писать напрямую: создаёт `background_jobs` со статусом `queued` и
сразу возвращает `202` с `job_id`; фронтенд опрашивает `GET /jobs/{id}` (общий эндпоинт для импортов и,
позже, отчётов). Идемпотентность: применение снова того же `import_id` при уже `succeeded`/`running`
задаче возвращает существующий `job_id` вместо новой записи (та же проверка `409`, что уже есть, плюс
защита от гонки двух одновременных «Apply»).

**Откат (rollback).** Только «безопасный» случай из ТЗ («when later records do not depend on the
imported changes»): применённый батч хранит список `(entity, id, was_new)` по каждой затронутой записи;
откат в отдельной фоновой задаче удаляет записи с `was_new=true` и не имеющие последующих изменений
(проверка по `updated_at`/аудиту, созданному после применения импорта) и возвращает предыдущие значения
для `was_new=false` из хранимого «before»-снимка отчёта предпросмотра. Если хоть одна запись имеет более
позднее изменение — откат для неё отклоняется, остальные откатываются, итог — частичный откат с явным
отчётом (это осознанно **не** all-or-nothing: обратное требование сделало бы откат невозможным почти
всегда на активной системе).

### 3.3 Документы: модель и жизненный цикл

```
Document (id, entity_type, entity_id, title, doc_type, academic_year, owner_user_id, source,
          visibility, created_at)
DocumentVersion (id, document_id, version_number, storage_key, sha256, size_bytes, content_type,
                 filename, state [Uploaded/Quarantined/Validated/Rejected/Linked], scan_result,
                 uploaded_by_user_id, created_at)
```

`entity_type`/`entity_id` — полиморфная привязка к `university`/`launch`/`contract` (по брифу — «program,
product» тоже, но без моделей этих сущностей ссылка на них не имеет смысла; ограничиваем целями, которые
реально существуют: `university`, `launch`, `contract`). Новая загрузка того же логического документа
(тот же `document_id`, новый файл) создаёт `DocumentVersion` с следующим `version_number`; прежние версии
не удаляются и не перезаписываются («never overwrite historical evidence in place» — буквально).

Состояния версии — по разделу 5.3 брифа: `Uploaded → Quarantined → Validated → Linked` или `→ Rejected` на
любом шаге. Пока нет антивируса (см. решение в разделе 6), `Quarantined → Validated` выполняется
синхронно по контент-проверкам (сигнатура/MIME/расширение/размер/архив), `scan_result` = `'not_scanned'`
с явной пометкой в интерфейсе и API, а не тихой подменой на «проверено».

Хранение — тот же приём, что уже есть (`attachments_data`), но отдельный подкаталог `documents/` и
отдельный подкаталог `quarantine/` для файлов, ещё не прошедших проверку (файл переносится/переименовывается
из `quarantine/` в `documents/` только после `Validated`; при `Rejected` остаётся в `quarantine/` до
плановой очистки, никогда не становится доступным для скачивания).

### 3.4 Короткоживущие ссылки на скачивание

Поверх существующей сессионной защиты (не вместо неё): `GET /documents/{id}/download` при авторизованном
запросе выдаёт не файл напрямую, а перенаправление на `GET /documents/{id}/download?token=...&expires=...`
(HMAC подписанный токен с TTL, например 5 минут, ключ — из `SESSION_ENCRYPTION_KEY` или отдельный
`DOWNLOAD_LINK_KEY`). Токен-эндпоинт всё равно проверяет, что документ всё ещё в скоупе видимости на
момент скачивания (отзыв доступа между выдачей ссылки и скачиванием должен блокировать файл), т.е. это
защита от «ссылка гуляет в логах/истории браузера вечно», а не замена проверки прав.

### 3.5 `correlation_id`

Middleware в `main.py`: читает `X-Correlation-Id` от клиента или генерирует новый UUID, кладёт в
`request.state`, возвращает тем же заголовком в ответе, передаёт в `record_event` (новая колонка
`audit_events.correlation_id`) и в `background_jobs.correlation_id`.

## 5. Тесты (по разделу «Required tests» ТЗ)

Backend (pytest, PostgreSQL, шаблонная БД — существующий конвенции `conftest.py`):
валидный xlsx создаёт/обновляет; отсутствующее обязательное поле; неверный тип; дубликат внутри файла;
конфликт create/update; сущность/поле вне скоупа пользователя → `403`/`404`; повторный `apply` —
идемпотентность (`409`, задача не дублируется); откат отменяемой и неотменяемой (уже изменённой) записи;
валидные PDF/DOCX — весь цикл состояний до `Linked`; несовпадение MIME/сигнатуры → `Rejected`; превышение
размера; зашифрованный/архивный файл; вредоносный тестовый файл (EICAR — стандартный безопасный тестовый
образец, если антивирус подключается, см. раздел 6); скачивание другой командой → `403`/`404`; новая
версия документа не удаляет старую, `GET` истории версий отдаёт обе.

Фронтенд (Vitest): выбор сущности меняет доступные поля мастера; сохранение/переиспользование
сопоставления; опрос статуса фоновой задачи без перезагрузки страницы; скачивание отчёта об ошибках;
загрузка PDF/DOCX с карточки вуза/взаимодействия; список версий документа; ролевые ограничения (нет прав
→ действие не отображается и не выполняется запрос).

E2E/интеграционные (то, что уже практикуется в проекте — проверка через реальный Compose-стенд, без ввода
паролей в форму Keycloak, D-130): полный цикл «загрузить xlsx → просмотр → применение фоновой задачи →
записи видны в CRM» на синтетическом файле; загрузка синтетического PDF и скачивание по короткоживущей
ссылке; попытка скачать после истечения TTL.

## 6. Решения владельца (подтверждены 2026-09-16)

| # | Вопрос | Решение | Запись |
|---|---|---|---|
| 1 | **Антивирус** | ClamAV — реальный движок, не эвристика. Документ остаётся `Quarantined` (`scan_result='pending'`) до ответа `clamd`; любое совпадение или ошибка сканера → `Rejected` (fail closed, никогда не помечается «безопасно» по умолчанию) | D-155 |

| 3 | **Целевые сущности первой волны импорта** | Университеты, контакты вуза, взаимодействия (создание); договоры (T-033) — тот же реестр импортёров, код не переписывается | D-157 |
| 4 | **`crm-admin` и содержимое документов** | Полный доступ сохраняется в Фазе 0; каждое обращение администратора — отдельная пометка в аудите для будущего break-glass (Phase 1 брифа, вне этой задачи) | D-158 |

| 6 | **Частичный (не all-or-nothing) режим применения импорта** | Не реализуем в Фазе 0 (бриф: «keep disabled by default») | Соответствует ТЗ |

   запуска; сохраняемые профили сопоставления; экспорт построчных ошибок; безопасный откат.
3. Модель `Document`/`DocumentVersion`, карантин-каталог, загрузка PDF/DOCX с карточек вуза и
   взаимодействия, версионирование, короткоживущие ссылки на скачивание.
4. Административный экран политик (форматы/размер/retention) — минимальный, одна страница.
5. Документация: `docs/api/imports.md` (обобщение), новый `docs/api/documents.md`,
   `docs/operations/backup.md` (том `documents_data` в резервное копирование, как уже сделано для
   `attachments_data`), пользовательская и административная инструкция.

Импорт договоров (существующий, T-033) и вложения к сменам статуса (T-041/042, существующие) **не
переделываются** — они уже соответствуют большей части требований брифа (карантин-подобная проверка,
SHA-256, скоуп, аудит) и явно вне регрессионного риска этой задачи, если только реестр импортёров не
сможет обернуть их без изменения поведения.

## 8. Риски

- **Заявленное соответствие ФСТЕК/152-ФЗ.** Раздел 9 брифа сам говорит: «Compliance cannot be confirmed
  from a prototype». Ничего в этом плане не заявляется как формально соответствующее — только как
  «спроектировано с учётом» (как и раньше в этом проекте, D-007 и общая дисциплина «не заявлять
  соответствие без подтверждения»).
- **Без антивируса** (решение 1 выше) — риск для метрики «0% опасных файлов» остаётся открытым до
  отдельного решения владельца; план явно показывает это в интерфейсе, а не скрывает.
- **Откат — не универсальный.** Частичный откат («часть записей уже изменена после импорта») — осознанное
  ограничение объёма, не пропущенный случай.
- **Новый процесс (воркер) в Compose** увеличивает объём инфраструктуры для локальной разработки и CI;
  тесты воркера потребуют либо реального цикла опроса в интеграционных тестах, либо прямого вызова
  функции обработки задачи в модульных тестах (предпочтительно для скорости CI).
