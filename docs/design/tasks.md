# Задачи (рабочее пространство, шаблоны планов)

Статус: готово (все 7 слайсов из технического задания завершены — см. «Порядок реализации» ниже),
плюс пост-базовые UX-доработки (ниже). Решения — D-158–D-208 в `docs/decisions.md`.
Заменяет модуль-заглушку `tasks` (`launch_id`, `title`, свободный `owner`, обязательный `deadline`,
булево `done`). Референс поведения — Bitrix24 (не код, не брендинг, не копия дизайна).

## Пост-базовые UX-доработки

После семи слайсов ТЗ (зафиксированы отдельным базовым коммитом) владелец продукта заказывает
точечные UX-правки поверх готового модуля, каждая — фокусированным слайсом со своим коммитом
(D-192–). Первая: постоянная встроенная панель фильтров в представлениях «Список»/«Сроки» заменена
на кнопку «Фильтры» с счётчиком применённых фильтров, открывающую диалог с черновым состоянием
(отмена/Escape/фон не применяют изменения, «Сохранить» — применяет и сохраняет на сервере per
`{view}:{scope}`); видимых вкладок области видимости стало 5 из 7 (`created`/`observing` остаются
полностью рабочими в API, просто без вкладки). См. D-192–D-195.

Вторая (отдельный слайс, отдельный коммит): представление «Сроки». Каждая группа срока — сворачиваемый
`<details>` (по умолчанию раскрыт), в строке задачи теперь виден приоритет (паритет со «Список»), а
обрезанный сервером хвост группы («и ещё N…») стал настоящей ссылкой в «Список» с точным фильтром этой
группы вместо тупика — потребовалось одно новое значение `later` в общем `DeadlinePreset`. См. D-196–D-197.
*(Полностью заменено пятым шагом ниже — канбан-доской; `later` остаётся в `DeadlinePreset` и
используется дальше.)*

Третья: лента событий на странице задачи теперь идёт сразу после блока статуса (была последней);
поля «Статус»/«Приоритет» в диалоге фильтров оформлены как карточки с двухколоночной сеткой чекбоксов;
у подзадач появился ответственный — селектор при создании и точечный `PATCH /tasks/{id}/assignees`
для переназначения одной подзадачи, не трогающий со-исполнителей/наблюдателей (в отличие от полного
`PUT /members`), с контролем видимым только тем, у кого есть право переназначения (правило
`TaskAction.REASSIGN`, проверено и на сервере). См. D-198–D-201.

Четвёртая: общая инфраструктура пользовательских колонок для обеих досок и её применение к «Мой план».
Четыре новых JSONB-поля в `task_user_preferences` (`planner_custom_columns`, `planner_custom_members` —
и их пара `deadline_*` для следующего шага, миграция 0013) хранят личные колонки поверх существующих
`planner_columns`/`planner_positions`: заголовок, порядок среди системных колонок, и карту
«задача → личная колонка» (единственное состояние, не выводимое из полей самой задачи). Общая логика —
`boardColumns.ts`/`useBoardColumnActions` (добавить/переименовать/удалить/переместить колонку,
распределить задачи по колонкам с учётом личного переопределения) — теперь используется «Мой план» и
рассчитана на «Сроки» без изменений. Перенос карточки в личную колонку не меняет реальный статус
(и в будущем — срок); перенос из личной колонки обратно в системную — обычный проверенный переход
статуса, который также снимает переопределение. Перемещение и переименование/удаление колонок —
кнопки на заголовке колонки (клавиатурно доступны), не drag — drag остаётся только для карточек.
См. D-202–D-204.

Пятая: «Сроки» перестроено в горизонтальную канбан-доску той же архитектуры, что «Мой план» —
`deadline_columns`/`deadline_positions`/`deadline_custom_columns`/`deadline_custom_members`,
`resolveDeadlineColumnOrder()` гарантирует, что все 6 колонок по срокам показаны всегда (в отличие
от «Мой план», где системную колонку можно скрыть). Перетаскивание карточки в системную колонку
переиспользует существующий `PATCH /tasks/{id}` (без нового эндпоинта) — те же права
(`TaskAction.CHANGE_DEADLINE`), оптимистичная блокировка по версии и событие активности, что и обычное
редактирование задачи; при ошибке карточка остаётся на месте, потому что её колонка всегда выводится
из данных запроса, а не меняется оптимистично. Кнопка «+» на колонке открывает существующую форму
создания с предзаполненным сроком по точному соответствию: `overdue`→вчера, `today`→сегодня,
`this_week`→конец текущей недели, `next_week`→конец следующей недели, `later`→первый день после
следующей недели, `no_deadline`→без срока. Доска показывает только активные задачи (`active=true`,
принудительно — колонки для «Завершено» нет, как и раньше у серверной группировки). Старый серверно
группированный путь (`TaskDeadlineView`, `useDeadlineGroups`, `GET /tasks/deadline-groups` на
фронтенде) удалён с фронтенда как неиспользуемый; сам эндпоинт на бэкенде оставлен нетронутым.
См. D-205–D-207.

Как и «Мой план» (см. выше), доска загружает до 100 активных задач одним запросом — тот же практический
предел, что и у планировщика; пересмотреть при реальной необходимости (слайс производительности), не
заранее.

Шестая: поле «Договор» убрано из формы создания задачи (и не появлялось в форме редактирования —
там его никогда не было). Форма больше не запрашивает список договоров и не отправляет `contract_id`
при создании; поле «Взаимодействие», ранее делившее строку с «Договор» в `.form-row`, теперь занимает
её целиком, без пустой колонки. Договор остаётся полноценной частью модели и API (эндпоинты, миграции,
сам модуль «Договоры» не тронуты); существующая историческая связь задачи с договором по-прежнему
видна в карточке задачи как read-only значение. См. D-208.

Седьмая: «Список» переделан по образцу CRM (Битрикс24, Asana). Над таблицей — одна строка: область
видимости (выпадающий список вместо второго ряда вкладок), поле поиска с применёнными фильтрами-чипами
внутри и кнопкой «Фильтры», компактный переключатель «Список/Сроки/Мой план», «Создать задачу». Ниже —
одна строка счётчиков-фильтров («Открытые», «Просрочено», «Сегодня», «На проверке», «Без срока»;
повторный клик снимает фильтр). Сортировка — кликом по заголовку колонки. В диалоге фильтров вместо
«Чек-лист» и «Активность» — «Исполнитель» и «Постановщик». Строка показывает под названием вуз ·
взаимодействие и прогресс чек-листа/подзадач/число комментариев, срок — относительно и цветом
(«Просрочена на 4 дня», «Сегодня», «Через 3 дня»), исполнителей — аватарами; сверху строка быстрой
задачи (Enter — создать, исполнитель — текущий пользователь). См. D-217.

Восьмая: карточка задачи — две колонки. Слева название (правка на месте: карандаш, Enter/уход с поля —
сохранить, Escape — отмена), кнопки смены статуса (следующий шаг — основная кнопка), описание, затем
лента событий → чек-лист → подзадачи → комментарии (порядок D-198 сохранён). Справа — закреплённая
панель свойств: срок, плановое начало, приоритет, «Требует проверки», исполнители меняются прямо в ней.
Отдельной формы «Изменить» больше нет. См. D-218.

Девятая: карточки досок «Сроки» и «Мой план» — общая компактная карточка: название, срок цветной
плашкой, приоритет только для высокого/срочного, статус только на «Сроки», вуз · взаимодействие,
аватары исполнителей и прогресс. Кнопки ↑/↓ и «Переместить» (альтернатива перетаскиванию с клавиатуры)
убраны в меню «⋯» на карточке. См. D-219.

## Понимание задачи

UniCRM помогает сотрудникам школы РТК ИТ понимать, что нужно сделать при начале и ведении
сотрудничества с вузом. Модуль «Задачи» — не просто список дел при запуске вуза: это
операционное пространство с ролевыми областями видимости, представлениями (список, сроки, личный
план), чек-листами, подзадачами, потоком согласования и — центральный сценарий — шаблонами планов
задач, которые за одну транзакцию разворачивают типовой процесс адаптации вуза (14 этапов
существующего процесса) в набор связанных, редактируемых задач.

Задача не обязана быть привязана к вузу — обычная внутренняя задача создаётся без вуза.
Необязательные связи: один вуз, одно взаимодействие (`launches`, «программа/лонч»), один договор.
Если выбраны взаимодействие или договор — сверяем, что они принадлежат выбранному вузу (или
выводим вуз из них, если вуз не указан явно); противоречивые связи отклоняются.

Не в этой поставке: страница «Календарь» (полноценная, для всех задач), Gantt, учёт времени,
рейтинги продуктивности, генерация email/SMS/Telegram, полноценная матрица прав в Settings —
список полностью соответствует разделу «Out of scope» технического задания.

**Примечание о расхождении во входных данных:** первое короткое сообщение задачи упоминало
календарь как «ещё одну вкладку» этой поставки; подробное техническое задание, которое пришло следом
и является основным источником требований, явно относит глобальную страницу «Календарь» к
следующей поставке. Здесь и далее руководствуюсь подробным ТЗ как более полным и обдуманным
источником; календарь не реализуется в этом слайсе. Задачи хранят `planned_start`, `deadline`
и связи с вузом/взаимодействием/договором — этого достаточно, чтобы будущий календарь строился
без новой миграции.

## Выбор базовой ветки

Ветка `ai/tasks-workspace` создана от `ai/phone-verification` (актуальный `origin`), а не от
`ai/auth-registration`/`ai/registration-polish` — потому что именно в этой линии истории уже есть
полный набор существующих модулей, от которых явно требуется переиспользование (процессы/статусы,
аудит, справочники, договоры, загрузка вложений), тогда как линия `ai/auth-registration` — другая,
разошедшаяся история (согласно более раннему исследованию репозитория в этой же сессии), где эти
модули присутствуют по другой причине и без ревью с точки зрения текущей задачи. Модель `Task`
(`launch_id`, `title`, `owner`, `deadline`, `done`) идентична на обеих ветках — переименование в
UniCrm на эту ветку не переносилось (вне рамок этой задачи); заметно как известный разрыв.

## Модель данных

Существующая таблица `tasks` не пересоздаётся — расширяется миграцией с обратной совместимостью
(старые колонки `owner`, `done` остаются в БД, но приложение больше их не читает и не пишет после
миграции; они не удаляются, пока миграция и совместимость не подтверждены проверками).

**tasks** (расширенная): `id`, `title` (обязательно, ≤200), `description`, `status` (код,
`CheckConstraint` по стабильному набору), `priority` (код), `deadline` (nullable, было обязательным),
`planned_start` (nullable), `creator_id` (FK users, nullable — см. миграцию владельца ниже),
`university_id` / `launch_id` / `contract_id` (FK, все nullable; `launch_id` — уже существующая
колонка, снимается NOT NULL), `parent_task_id` (self-FK, nullable — один уровень подзадач),
`approval_required` (bool), `require_checklist_complete` (bool, default true),
`completed_at`/`completed_by_user_id`, `archived_at`/`archived_by_user_id` (мягкий архив вместо
удаления), `origin_plan_run_id` (FK, nullable), `origin_template_step_key` (nullable — для колонки
«исходный план задач» даже после того, как строка запуска устареет), `created_at`, `updated_at`,
`version` (оптимistic locking через `version_id_col` SQLAlchemy — конфликт параллельного изменения
возвращается как `409 CONFLICT`, а не тихо перезаписывается).

Стабильные коды (хранятся и отдаются в API как есть; русские подписи — только в интерфейсе, по
образцу `TRANSFER_STATUS_LABELS`):
- `status`: `new → in_progress → awaiting_review → completed`, плюс `deferred`, `cancelled`.
- `priority`: `low`, `normal`, `high`, `urgent`.
- роль участника (`task_members.role`): `assignee`, `participant` (со-исполнитель), `observer`.

**task_members** — (`task_id`, `user_id`, `role`), уникальность по тройке. Несколько исполнителей —
несколько строк с `role='assignee'` на одной задаче (задача не дублируется).

**task_checklist_items** — `id`, `task_id`, `title`, `position`, `is_done`, `assignee_user_id`
(nullable), `deadline` (nullable), `completed_by_user_id`, `completed_at`.

**task_tags** / **task_tag_links** — переиспользуемый справочник тегов + связь many-to-many.

**task_comments** — `id`, `task_id`, `author_user_id`, `body`, `created_at`. Отдельная таблица:
существующий `StatusChange.comment` — это один комментарий на смену статуса взаимодействия, не
многократный тред. Как и в `workflow_routes.py`, аудит-событие фиксирует только факт комментария,
не текст (в нём могут быть персональные данные).

**task_attachments** — та же схема, что у существующих `attachments`, но привязана к `task_id`
(и опционально к `comment_id`). Загрузка переиспользует существующую проверку файлов
(`store_upload`/`FILE_TYPES`/`clean_filename` из `workflow_routes.py`) — выношу их в общий
`app/uploads.py`, чтобы не дублировать между процессами и задачами.

**task_events** — таймлайн одной задачи (создание, смена статуса, смена срока, переназначение,
завершение пункта чек-листа, согласование, повторное открытие, архивация) — актёр, было/стало,
комментарий, время. Тот же приём, что уже есть у пары `StatusChange` (таймлайн одного взаимодействия)
+ `AuditEvent` (общий аудит, `entity_type='task'`) — обе записи пишутся при каждой мутации, как и
сейчас для взаимодействий.

**task_plan_templates** / **task_plan_template_steps** / **task_plan_template_step_checklist_items** —
шаблон, его шаги по порядку (заголовок/описание по умолчанию, правило назначения — конкретный
пользователь / ответственный по взаимодействию / менеджер вуза / автор плана / вручную, смещение
старта и срока в календарных или рабочих днях, приоритет, зависимость от предыдущего шага,
обязательность согласования, необязательность шага), чек-лист каждого шага.

**task_plan_runs** — `id`, `template_id`, `template_snapshot` (JSONB — полная копия шаблона и шагов
на момент запуска), `university_id`, `launch_id` (nullable), `started_by_user_id`, `start_date`,
`created_at`. Последующее редактирование шаблона не переписывает уже созданные задачи — они хранят
`origin_plan_run_id` и опираются на `template_snapshot`, а не на живой шаблон.

**task_user_preferences** — `user_id` (PK), `list_columns` (JSONB, видимые колонки списка),
`planner_columns` (JSONB, личные колонки «Мой план»), `planner_positions` (JSONB, позиции карточек).
Именно то немногое, что спецификация просит хранить на сервере; фильтры/сортировка/пагинация/
представление остаются в query-параметрах URL — сервер их не хранит.

Внешние ключи, индексы под фильтры (`status`, `deadline`, `creator_id`, `university_id` и т.д.),
`CheckConstraint` на коды — по образцу `contracts`/`workflow_statuses`.

## Стратегия миграции

Одна обратимая Alembic-миграция (`00010_tasks_workspace.py` и далее по счётчику), без потери
существующих строк:
1. Добавить новые колонки в `tasks` (nullable, с разумными server_default, где применимо).
2. `status = 'completed' if done else 'new'` для каждой существующей строки.
3. `creator_id`: сопоставить `owner` (свободный текст) с активным пользователем CRM только при
   ровно одном совпадении по `lower(trim(full_name))`; иначе `creator_id` остаётся `NULL`, а
   исходный текст остаётся в нетронутой колонке `owner` — это и есть сигнал «требует внимания
   администратора» (нет отдельного флага: `creator_id IS NULL AND owner <> ''`).
4. `launch_id` остаётся как есть (уже заполнен у всех существующих строк) — становится
   необязательной связью «взаимодействие» для новых задач, снимается `NOT NULL`.
5. `deadline` сохраняется как есть у существующих строк, становится nullable для новых.
6. Колонки `owner`, `done` не удаляются в этой миграции (условие технического задания); ссылки на
   них в коде приложения убираются полностью — необратимая часть документируется в самой миграции
   и в `docs/decisions.md`.

## API

Новый роутер `backend/app/task_routes.py`, префикс `/api/v1`, тег «Задачи» — по образцу
`workflow_routes.py` (Pydantic-схемы `*Out`/`*In`/`*Patch`, `field_error`/`flush_or_conflict`,
`record_event` в той же транзакции, `AppError`/`ErrorCode` из `app/errors.py`, CSRF — уже
проверяется централизованно в `current_auth` для всех «небезопасных» методов, ничего дополнительно
делать не нужно).

Основные ресурсы: пагинированный список (`GET /tasks`, серверная сортировка/фильтры/allowlist),
счётчики (`GET /tasks/counters`), создание/чтение/правка/архив/восстановление (`POST|GET|PATCH
/tasks`, `/tasks/{id}`, `/tasks/{id}/archive`, `/tasks/{id}/restore`), переход статуса
(`POST /tasks/{id}/status`), участники (`PUT /tasks/{id}/members`), чек-лист (`POST/PATCH/DELETE
/tasks/{id}/checklist-items`, `PUT .../checklist-order`), подзадачи (обычный `POST /tasks` с
`parent_task_id`), комментарии и вложения (`GET/POST /tasks/{id}/comments`, `multipart/form-data`,
как `change_status`), таймлайн (`GET /tasks/{id}/activity`), массовые действия (`POST
/tasks/bulk/{status|deadline|members|tags|archive}` — сервер проверяет права на каждую выбранную
задачу отдельно), настройки представления (`GET/PUT /tasks/preferences`), шаблоны планов (`GET/POST
/task-plan-templates`, шаги, `POST .../preview`, `POST .../generate` — транзакционно), мониторинг
(`GET /tasks/monitoring`). Компактные ссылки на пользователей/вузы/взаимодействия/договоры в ответах
(не зеркалирование таблиц один в один) — как уже делает `contract_out`. Документируется в OpenAPI
через обычные `response_model` (docs/api/tasks.md добавляется по итогам слайса 2).

## Политика прав

Новый модуль `backend/app/task_policy.py` — единая точка принятия решений, а не рассеянные проверки
роли по роутам (по аналогии с `sees_all`/`university_scope` в `catalog_routes.py`, но шире:
участие в задаче — самостоятельное измерение, не только роль CRM). Действия: `view`, `create`,
`edit`, `reassign`, `change_deadline`, `complete`, `reopen`, `archive`, `edit_checklist`,
`manage_templates`, `export`, `manage_permissions` — под каждым набором ролей уже сейчас, но
структурировано так, чтобы будущая матрица Settings → «Пользователи и роли» могла подменить эту
логику данными без переписывания роутов. `crm-user` видит задачи, которые создал, где он
исполнитель/со-исполнитель/наблюдатель, либо задачи вузов из своей зоны ответственности
(переиспользуется `managed_university_ids`); `crm-supervisor`/`crm-admin` — `sees_all()`, уже
существующая функция. Тесты на прямой обход API в обход интерфейса — обязательная часть слайса 1
(раздел «Обязательные тесты» технического задания).

## Границы компонентов фронтенда

`frontend/src/pages/tasks/` — `TasksPage.tsx` остаётся тонким: состояние URL (представление, фильтры,
сортировка, пагинация — `useSearchParams`), переключение видов, открытие карточки как оверлея с
сохранением списка позади. Отдельные файлы: `TaskCounters`, `TaskScopeTabs`, `TaskFilterBar` (чипы +
поповер, «Сбросить фильтры», предустановки), `TaskViewSwitcher`, `TaskListView` (таблица, серверная
пагинация/сортировка, выбор строк, настраиваемые колонки), `TaskColumnPicker`, `TaskBulkActionsBar`,
`TaskDeadlineView` (группировка: просрочено/сегодня/на этой неделе/на следующей/позже/без
срока/завершено), `TaskPlannerView` («Мой план» — личные колонки, drag-and-drop), `TaskDrawer`
(маршрут `/tasks/:id`, также открывается поверх списка), `TaskQuickCreateForm`,
`TaskDetailForm`, `TaskChecklist`, `TaskComments`, `TaskActivity`, `TaskSubtasksList`. Отдельная
вторичная страница `TaskTemplatesPage.tsx` (редактор шаблонов планов — доступен из настроек раздела
«Задачи», не новый пункт верхнего уровня навигации, как явно требует ТЗ; страница также сама
проверяет `canEditWorkflows`, как `WorkflowsPage`, — маршрут доступен по прямому URL независимо от
того, откуда на него ведёт ссылка). Реализация слайса 5 вынесла типы и хуки шаблонов планов в
отдельный `frontend/src/api/planTemplates.ts` (не в `api/tasks.ts` — модуль достаточно большой и
самостоятельный), а мастер запуска плана и прогресс (`TaskPlanSection.tsx`, показывается на
странице вуза) — в `frontend/src/components/tasks/`. API-клиент `frontend/src/api/tasks.ts` — типы
и хуки TanStack Query по образцу `api/workflows.ts` (`queryKeys`, `invalidate`, `apiRequest`).

**Новая зависимость:** для drag-and-drop в «Мой план» (и клавиатурная альтернатива — обязательное
требование ТЗ) добавляю `@dnd-kit/core` + `@dnd-kit/sortable` — в репозитории пока нет ни одной
DnD-библиотеки, а перетаскивание, доступное с клавиатуры и читаемое скринридером, с нуля — источник
трудноуловимых ошибок; `@dnd-kit` — стандартный лёгкий выбор именно для этого. Флагирую решение
здесь, а не молча добавляю в `package.json`; это не деструктивное действие, не платный сервис и не
блокирующее продуктовое решение, поэтому продолжаю без ожидания подтверждения (по явному разрешению
в задаче), но открыт к другому выбору, если он есть.

Реализация слайса 6 разбила `TaskPlannerView` на несколько файлов вместо одного: `plannerLogic.ts`
(чистые функции — группировка по статусу, применение сохранённого ручного порядка, проверка
допустимости перехода — без React, отдельно тестируемые), `PlannerCard.tsx` (карточка: перетаскивание
через `useSortable`, кнопки «выше/ниже» и `<select>` «Переместить» как независимая от drag-and-drop
клавиатурная альтернатива, использующая тот же обработчик), `PlannerColumnSettings.tsx` (видимость и
порядок колонок), `StatusCommentModal.tsx` (вынесенная из `TaskStatusActions.tsx` форма обязательного
комментария при возврате на доработку — теперь общая для карточки статуса и доски). Личные колонки —
не произвольные, а выбранный пользователем поднабор/порядок уже существующих статусов задачи
(`new`/`in_progress`/`awaiting_review`/`deferred`/`completed`); перетаскивание карточки между
колонками — обычный переход статуса через `POST /tasks/{id}/status`, проверяемый по той же таблице
переходов, что и кнопки на карточке задачи (D-180).

## Порядок реализации (как в техническом задании)

1. **Этот слайс** — миграция, доменная модель, политика прав, события аудита, обратно совместимое
   чтение старых записей.
2. Создание самостоятельных и связанных задач, несколько исполнителей, необязательный срок,
   постоянные ссылки (`/tasks/:id`), представление «Список».
3. Поток статусов, согласование, чек-листы, подзадачи, комментарии, таймлайн, ограничения завершения.
4. Фильтры, счётчики, настраиваемые колонки, массовые действия, представление «Сроки».
5. Шаблоны планов, предпросмотр, транзакционная генерация, прогресс плана вуза.
6. «Мой план», drag-and-drop, клавиатурная альтернатива, персональные настройки.
7. Производительность, отзывчивость на мобильных, доступность, проверка миграции, тесты, сборка.

Каждый слайс остаётся рабочим (собирается, проходит тесты) до перехода к следующему — приложение не
остаётся между несовместимыми состояниями схемы и фронтенда.
