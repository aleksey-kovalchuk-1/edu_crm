# Справочники: вузы, ИТ-направления, ИТ-продукты, ответственные, договоры

Статус: проект для задач T-030–T-034 и областей видимости данных T-022. Решения — D-136–D-141 в `docs/decisions.md`.

## Что требует спецификация

- ИТ-продукты, ИТ-направления, перечень вузов и ответственных хранятся как справочники в базе CRM и обновляются загрузкой xls/xlsx по согласованному сопоставлению полей.
- Поля загрузки: наименование вуза, вендор, программное обеспечение, номер договора, подписание лицензии, срок действия лицензии (один год), статус передачи, ФИО менеджера, ответственные от вуза, комментарий.
- Руководитель меняет, удаляет и назначает ответственных пользователей за вузы; администратор разграничивает пользователей по доступу к данным.

## Сущности

| Таблица | Назначение | Ключевые поля | Уникальность |
|---|---|---|---|
| `universities` (есть) | Учебные заведения | `name`, `city`, `contact` (устаревшее текстовое поле), новые: `short_name`, `region`, `website`, `is_active` | `name` |
| `it_directions` | ИТ-направления (DevOps, QA, …) | `name`, `description`, `is_active` | `name` |
| `it_products` | ИТ-продукты | `vendor`, `name` (программное обеспечение), `description`, `is_active` | (`vendor`, `name`) |
| `it_product_directions` | Направления продукта | `it_product_id`, `it_direction_id` | пара |
| `university_contacts` | Ответственные от вуза (персональные данные) | `university_id`, `full_name`, `position`, `email`, `phone`, `comment`, `is_active` | (`university_id`, `full_name`) |
| `university_managers` | Ответственные от ИТ-школы (пользователи CRM) за вуз | `university_id`, `user_id`, `assigned_at`, `assigned_by_user_id` | пара |
| `contracts` | Договоры и лицензии | `contract_number`, `university_id`, `it_product_id`, `signed_at` (подписание лицензии), `valid_until`, `transfer_status`, `manager_user_id`, `manager_name`, `comment`, `created_at`, `updated_at` | `contract_number` |
| `contract_contacts` | Ответственные от вуза по договору | `contract_id`, `university_contact_id` | пара |

Текстовые поля с русскими значениями используют сортировку `ru-RU-x-icu`. Изменения записываются в журнал действий.

## Правила

- **Срок действия лицензии.** Если при создании или загрузке не указан `valid_until`, он вычисляется как `signed_at` + 1 год (29 февраля → 28 февраля следующего года). Значение хранится и может быть изменено вручную; `valid_until` не может быть раньше `signed_at`.
- **Статус передачи** (материалов, лицензий и документации): `not_started` «Не начата», `in_progress` «Идёт передача», `transferred` «Передано», `cancelled` «Отменено».
- **Менеджер договора.** При загрузке ФИО менеджера сопоставляется с пользователями CRM по полному имени (без учёта регистра и лишних пробелов). Если совпадения нет или их несколько, ФИО сохраняется в `manager_name`, а строка отмечается в отчёте загрузки; учётные записи автоматически не создаются.
- **Удаление.** Записи справочников не удаляются физически, если на них есть ссылки: они деактивируются (`is_active = false`) и скрываются из выбора. Физическое удаление назначения ответственного (`university_managers`) допускается и записывается в журнал.

## Права и видимость (D-103)

| Действие | Менеджер | Руководитель | Администратор |
|---|---|---|---|
| Просмотр вузов, договоров, контактов | Только вузы, где он назначен ответственным | Все | Все |
| Создание и изменение договоров и контактов | В своих вузах | Все | Все |
| Ведение справочников направлений, продуктов, вузов | Нет | Да | Да |
| Назначение и снятие ответственных за вуз | Нет | Да | Да |
| Загрузка xls/xlsx | Нет | Да | Да |

Области видимости применяются в SQL-запросах, а не фильтрацией в интерфейсе. Менеджер без назначений видит пустые списки. Существующие «взаимодействия» (запуски) до переработки процессов (T-040) видимы по тем же правилам через свой вуз.

## API (T-031)

- `GET /api/v1/it-directions`, `GET /api/v1/it-products`, `GET /api/v1/universities`, `GET /api/v1/universities/{id}`, `GET /api/v1/contracts`, `GET /api/v1/universities/{id}/contacts` — фильтры (`q`, `include_inactive`, для договоров: `university_id`, `it_product_id`, `it_direction_id`, `manager_user_id`, `transfer_status`, `signed_from`, `signed_to`, `valid_until_to`), сортировка, пагинация договоров (`limit`, `offset`, в ответе `total`). Точный контракт — `docs/api/catalogs.md`.
- `POST`/`PATCH` для каждой сущности; деактивация через `PATCH {is_active: false}`.
- `PUT /api/v1/universities/{id}/managers` — полный список ответственных пользователей вуза (руководитель, администратор).
- Ошибки — коды из `docs/api/errors.md`; дубликаты уникальных полей → `409 CONFLICT` с полем в `details`.

## Открытые вопросы к владельцу

- Образец xls/xlsx и согласованное сопоставление столбцов.
- Окончательный перечень статусов передачи.
- Нужна ли синхронизация списка пользователей из Keycloak (сейчас пользователь появляется в CRM после первого входа).
