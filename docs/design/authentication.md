# Аутентификация и сессии (Keycloak)

Статус: реализовано в T-020–T-024; доработки по итогам проверки безопасности (привязка входа к браузеру, поведение при недоступности Keycloak, выход на стороне сервера) внедряются — ход работ в `docs/night-report.md`. Решения — D-104, D-117, D-118, D-122–D-126, D-132–D-135 в `docs/decisions.md`.

## Цели

- Вход только через Keycloak (требование спецификации); собственных паролей в CRM нет.
- Токены Keycloak не попадают в JavaScript браузера.
- Отключение пользователя или завершение его сессии в Keycloak прекращает доступ к CRM в течение нескольких минут.
- Работает при нескольких процессах API (любой процесс может завершить вход).

## Компоненты

| Компонент | Роль |
|---|---|
| Keycloak `26.7.3` (режим `start`, БД `keycloak` в PostgreSQL) | Учётные записи, пароли, роли `crm-user`, `crm-supervisor`, `crm-admin`, защита от перебора |
| nginx (`:8080`) | Единая точка входа: `/` — интерфейс, `/api/` — API, `/auth/` — Keycloak |
| API (FastAPI) | Конфиденциальный OIDC-клиент `edu-crm-api`: код авторизации + PKCE S256; хранит сессии в PostgreSQL |
| Браузер | Получает только cookie `edu_crm_session` (HttpOnly, SameSite=Lax) и CSRF-токен |

Keycloak публикуется через nginx по пути `/auth`, поэтому издатель токенов (`iss`) стабилен: `http://localhost:8080/auth/realms/edu-crm`. API обращается к Keycloak напрямую по сети Compose (`http://keycloak:8080/auth`) — включён `KC_HOSTNAME_BACKCHANNEL_DYNAMIC`.

## Поток входа

1. Интерфейс получает `401 UNAUTHENTICATED` и перенаправляет браузер на `GET /api/v1/auth/login?next=<путь>`.
2. API создаёт запись `login_states` (хэш `state`, `nonce`, `code_verifier`, путь возврата, хэш значения cookie браузера, срок 10 минут), выставляет короткоживущую cookie `edu_crm_login` (HttpOnly, SameSite=Lax, 10 минут) со случайным значением и перенаправляет на страницу входа Keycloak.
3. Keycloak возвращает браузер на `GET /api/v1/auth/callback?code&state`.
4. API однократно использует `state` (запись удаляется), проверяет, что cookie `edu_crm_login` этого браузера совпадает с сохранённым хэшем (иначе чужую ссылку на завершение входа можно подсунуть жертве — login CSRF), обменивает код на токены (секрет клиента + `code_verifier`), проверяет ID-токен: подпись по JWKS, `iss`, `aud`, `azp`, срок действия и возраст (`iat` не старше 10 минут), `nonce`.
5. Из токена берутся `sub`, `email`, `name` и роли `crm-*` (встроенные роли Keycloak отбрасываются). Запись `users` создаётся или обновляется.
6. Создаётся сессия: в БД хранится SHA-256 от случайного токена, CSRF-токен, срок, IP и User-Agent, а также refresh-токен Keycloak в зашифрованном виде (ключ `SESSION_ENCRYPTION_KEY`).
7. Браузер получает cookie и перенаправляется на путь возврата. Разрешены только относительные пути внутри приложения (защита от открытого редиректа).

## Проверка сессии на каждом запросе

- Cookie → хэш → действующая, не отозванная сессия активного пользователя; иначе `401 UNAUTHENTICATED`.
- Если с последней сверки с Keycloak прошло больше 120 секунд, API блокирует строку сессии, перечитывает её из базы (другой запрос мог уже обновить токен) и при необходимости обновляет токены по refresh-токену. Keycloak выдаёт refresh-токен однократно, поэтому без блокировки и перечитывания параллельные запросы отзывали бы собственную сессию.
- Явный отказ Keycloak (`invalid_grant`: пользователь отключён, сессия Keycloak завершена), несовпадение субъекта, ответ без ID-токена или потеря всех ролей CRM отзывают сессию → `401 UNAUTHENTICATED`. Роли обновляются из нового токена.
- Если Keycloak недоступен (сетевая ошибка, ответ 5xx, недоступны ключи подписи), сессия не отзывается: API отвечает `503 SERVICE_UNAVAILABLE`, и запрос можно повторить позже.
- Изменяющие запросы (`POST`, `PUT`, `PATCH`, `DELETE`) требуют заголовок `X-CSRF-Token`, совпадающий с токеном сессии, и допустимый `Origin`, если он передан; иначе `403 CSRF_INVALID` (отдельный код, чтобы интерфейс мог обновить токен и отличить это от нехватки прав `403 FORBIDDEN`).

## Выход

`POST /api/v1/auth/logout` сначала завершает сессию Keycloak на стороне сервера (back-channel logout по refresh-токену), затем отзывает сессию CRM, удаляет cookie и возвращает `logout_url` — адрес, на который переходит интерфейс (главная страница CRM, откуда снова потребуется вход с паролем). Если Keycloak недоступен, сессия CRM всё равно отзывается, а `logout_url` указывает на страницу выхода Keycloak (`end_session_endpoint` с `client_id` и `post_logout_redirect_uri`), чтобы пользователь мог завершить сессию Keycloak сам.

## Коды ошибок входа

| Код в `?auth_error=` | Источник | Значение |
|---|---|---|
| `LOGIN_CANCELLED` | API | Пользователь отменил вход в Keycloak |
| `LOGIN_EXPIRED` | API | Попытка входа устарела, уже использована или начата в другом браузере |
| `LOGIN_FAILED` | API | Keycloak отклонил вход или недоступен |
| `NO_ACCESS` | API | У учётной записи нет роли CRM или она отключена |
| `SESSION_NOT_SAVED` | Интерфейс | Повторное автоматическое перенаправление на вход за 15 секунд: браузер не сохранил cookie сессии; показывается совет разрешить cookie |

## Ограничение нагрузки на вход

- nginx ограничивает `GET /api/v1/auth/login`: 10 запросов в минуту с одного адреса, всплеск до 20.
- API не создаёт новых попыток входа, если незавершённых и не просроченных попыток уже слишком много (`429 RATE_LIMITED`); просроченные записи удаляются при каждом новом входе.

## API

| Метод | Назначение |
|---|---|
| `GET /api/v1/auth/login?next=` | Начать вход |
| `GET /api/v1/auth/callback` | Завершить вход |
| `GET /api/v1/auth/me` | Текущий пользователь, роли и CSRF-токен |
| `POST /api/v1/auth/logout` | Выйти |

## Таблицы

- `users`: `id`, `keycloak_sub` (уникальный), `email`, `full_name`, `roles` (кэш ролей `crm-*`), `is_active`, `created_at`, `last_login_at`.
- `sessions`: `id` (SHA-256 токена), `user_id`, `csrf_token`, `refresh_token_encrypted`, `created_at`, `expires_at`, `validated_at`, `revoked_at`, `ip`, `user_agent`.
- `login_states`: `state_hash`, `nonce`, `code_verifier`, `next_path`, `browser_hash` (SHA-256 значения cookie `edu_crm_login`), `created_at`, `expires_at`.

## Тестирование

Тесты не обращаются к настоящему Keycloak: генерируется RSA-ключ, JWKS и ответы token-endpoint подставляются через `httpx.MockTransport`. Проверяются: успешный вход, повторное использование `state`, неверные `iss`/`aud`/`nonce`/подпись, просроченная сессия, отзыв при неудачном обновлении, фильтрация ролей, CSRF и `Origin`, открытый редирект. Сквозной вход через настоящий Keycloak проверяется в браузере на стенде Docker Compose.
