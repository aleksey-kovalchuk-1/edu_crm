# Установка, сборка и проверка на Linux

Инструкция рассчитана на Linux с Docker Engine, плагином Docker Compose v2, `git` и `openssl`. Платформы: современный Ubuntu либо другой дистрибутив, где эти компоненты поддерживаются. Текущий публичный экземпляр размещён отдельно; исполнение всех шагов на конкретном Linux-сервере заказчика ещё требует приёмочной проверки.

## Подготовка

1. Выделить сервер и постоянное место для томов PostgreSQL и вложений; определить HTTPS-адрес, политику резервного копирования и доступ к SMTP/SMS, если нужны уведомления.
2. Получить исходный код из утверждённого релизного коммита. Не копировать рабочие `.env`, пароли и ключи между средами.
3. Из каталога проекта выполнить:

```bash
cp .env.example .env
scripts/generate-dev-secrets.sh
docker compose config --quiet
docker compose up --build -d
docker compose ps
```

Скрипт создаёт `deploy/local/keycloak.env` и `deploy/local/api.env` с правами владельца и случайными секретами. Пароли не печатаются в журнале команд и не должны попадать в Git. На первом запуске Keycloak и миграции БД требуют времени; `backend/docker-entrypoint.sh` применяет миграции до старта API, а `SEED_DEMO=true` добавляет демонстрационные записи только для учебного стенда. Для чистой рабочей БД задать `SEED_DEMO=false` **до первого запуска**. Роль `crm-superadmin` для рабочего пользователя настраивается отдельно по утверждённой процедуре и `INITIAL_SUPERADMIN_EMAIL`; не полагаться на демонстрационные аккаунты.

## Адреса и проверка

В локальной конфигурации: интерфейс `http://localhost:8080`, Swagger UI `http://localhost:8080/api/docs`, OpenAPI JSON `http://localhost:8080/api/openapi.json`, состояние API `http://localhost:8080/api/v1/health`. После входа открыть «Учебные заведения», «Взаимодействия», «Аналитика» и «Отчёты». Проверить скачивание JSON под двумя ролями с разным набором вузов. Порты Compose привязаны к loopback; для удалённого доступа нужен утверждённый HTTPS-прокси и корректная конфигурация внешнего URL/Keycloak, а не простое раскрытие портов.

## Миграции и обновление

`docker compose up --build -d` пересобирает сервисы из открытого исходного кода. Перед обновлением снять согласованную зашифрованную копию БД и вложений по [`docs/operations/backup.md`](../operations/backup.md). Миграции применяются при старте API; проверять их результат и состояние `docker compose ps` до открытия доступа пользователям. Текущий публичный Mac использует отдельный сценарий [`docs/operations/deploy-public.md`](../operations/deploy-public.md); он не является инструкцией установки на Linux заказчика.

## Локальная сборка и тесты без запуска интерфейса в Compose

Для серверных тестов нужен **отдельный тестовый сервер PostgreSQL или отдельный кластер**. Тестовый набор удаляет служебную базу с именем `edu_crm_test_template` на указанном сервере, поэтому не направлять его на рабочий кластер. После установки Python 3.12 и Node.js 22:

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r backend/requirements-dev.txt -c backend/constraints.txt
cd backend
TEST_DATABASE_URL='postgresql+psycopg://crm:<пароль>@127.0.0.1:55433/postgres' ../.venv/bin/python -m pytest -q
cd ../frontend
npm ci
npm test
npm run lint
npm run build
```

Значение `<пароль>` — секрет тестовой БД, не пример для рабочей среды. Для сборки образов отдельно можно выполнить `docker compose build api web`; зависимости берутся из зафиксированных manifest/lock-файлов.

## Эксплуатационные условия

Нужны регулярные копии БД и вложений, отдельное хранение ключей восстановления, контроль логов и места, обновление контейнеров и пакетов после проверки, ограничение доступа к секретам, мониторинг здоровья API/Keycloak/PostgreSQL. Уведомления и Superset запускаются только при включении соответствующих Compose-профилей. Параметры SMTP/SMS и внешнего адреса зависят от инфраструктуры заказчика и не входят в универсальную команду выше.
