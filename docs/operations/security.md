# Безопасность: что реализовано и что остаётся для продакшена (Phase 7)

Это описание фактически реализованных мер в прототипе `ai/integration-candidate` и того, что осталось сделать перед реальным развёртыванием в закрытой сети. **Соответствие 152-ФЗ или приказу ФСТЭК № 117 не заявляется и не проверялось** — ниже только перечень технических мер и их пределов.

## Реализовано

**Аутентификация.** Единственный поставщик идентичности — Keycloak (D-002); вход — сервер-к-серверу (backend-for-frontend) с PKCE, привязкой процесса логина к браузеру (cookie `edu_crm_login`, D-104/D-134), периодической ревалидацией сессии у Keycloak (D-125) и back-channel logout при выходе. Пароли пользователей не обрабатывает и не хранит CRM — только Keycloak. Само-регистрация ограничена доменом `.ru` и требует подтверждения e-mail и CAPTCHA (D-155–D-160 в `docs/decisions.md`).

**Авторизация.** Каждый маршрут API декларирует политику доступа — либо роль (`crm-user`/`crm-supervisor`/`crm-admin`), либо явную отдельную проверку (например, ключ коннектора); `tests/test_rbac.py::test_every_api_route_declares_an_access_policy` не даёт добавить маршрут без этого. Ролевая матрица и области видимости по вузам проверяются тестами на каждый эндпоинт, включая отчёты (`tests/test_reports.py`) и импорт (`tests/test_entity_import.py`, `tests/test_import_api.py`).

**Область видимости по вузам (D-141).** Менеджер (`crm-user`) видит и получает только данные закреплённых за ним вузов — во всех эндпоинтах, включая асинхронные отчёты (`app/reports.py::build_rows` пересчитывает область видимости во время выполнения фоновой задачи, а не по снимку на момент постановки в очередь, D-181) и прямые обращения к API, а не только через интерфейс (`tests/test_import_api.py::test_import_scope_and_permissions_cannot_be_bypassed_through_direct_api_calls`).

**CSRF.** Изменяющие запросы требуют совпадения `X-CSRF-Token` с токеном сессии и проверяют `Origin` против списка доверенных источников (D-104); мок-коннекторы (T-060) не используют сессии и CSRF намеренно — у них нет браузера, а авторизация — отдельный общий секрет `X-Connector-Key` (D-186).

**Неизменяемый журнал действий.** `audit_events` — только запись и чтение, без `UPDATE`/`DELETE` в коде (D-105/D-131); каждое изменяющее действие пишет ровно одну запись в той же транзакции. Расширено в этой интеграции: отключение статуса с переносом взаимодействий (D-179), формирование и скачивание отчёта (D-181), входящая доставка мок-коннектора (D-187) — во всех новых записях в `payload` только идентификаторы и счётчики, без текста комментариев, ФИО или иных персональных данных.

**Минимизация персональных данных.** Все демонстрационные данные — синтетические (D-007). Код подтверждения телефона хранится только как хеш (`phone_verification_codes.code_hash`) и никогда не попадает в журнал действий. Отчёты (`docs/api/reports.md`) и исходящая выгрузка коннекторов не отдают внутренние пути файловой системы, секреты или состояние сессии.

**Раздельное хранение.** Реляционные данные — только PostgreSQL; файлы (вложения, документы, отчёты) — на отдельных именованных томах Docker (`attachments_data`, `documents_data`, `reports_data`), никогда как BLOB в базе; скачивание — только через авторизованный эндпоинт API, путь на диске не раскрывается ни в одном ответе.

**Без внешнего ИИ.** Ни один компонент прототипа не обращается к внешнему LLM/ИИ-сервису.

**Проверка зависимостей.** `pip-audit -r backend/requirements.txt` и `npm audit --omit=dev` на момент этой интеграции — без известных уязвимостей (специального CI-шага не заводили: в проекте это не было настроено ранее, а разовая проверка не требует постоянной инфраструктуры).

## Не реализовано / остаётся для продакшена

- **Реальные секреты интеграций.** reCAPTCHA и SMTP работают на официальных тестовых значениях Google / локальном перехватчике Mailpit (D-158/D-159); `CONNECTOR_API_KEY` — один общий ключ для обоих мок-коннекторов без ротации (D-186) — для реального контракта нужен отдельный ключ на партнёра и процесс ротации.
- **TLS.** Порты Compose привязаны к `127.0.0.1`, `COOKIE_SECURE=false` для локальной разработки по HTTP; продакшен требует HTTPS-терминации (например, на балансировщике перед закрытой сетью) и `COOKIE_SECURE=true`.
- **Закрытая сеть.** Целевая архитектура — закрытая сеть (см. вводные к этой интеграции); прототип это не реализует и не эмулирует — сетевая изоляция, WAF и сегментация — задача развёртывания, не кода.
- **Ограничение доступа администратора к содержимому документов.** `crm-admin` сохраняет полный доступ; каждое обращение помечается в аудите отдельным полем для будущего break-glass-ограничения без изменения модели данных (D-168) — само ограничение не реализовано.
- **Формальное сопоставление с 152-ФЗ/ФСТЭК.** Не проводилось и не заявляется; список выше — это функциональные меры, а не аттестация.
