# Зашифрованные копии базы и вложений

Перед загрузкой реальных анкет проверьте резервное копирование **базы и тома вложений вместе**. Эти скрипты используют `age` и не создают открытый дамп или архив на диске. Утилита `age` должна быть установлена на машине, где запускают скрипты. Скрипты завершаются с ошибкой, если получатель или ключ для восстановления не указан.

## Ключи и место хранения

1. В доверенной среде создайте отдельный ключ резервных копий: `age-keygen -o /защищённый/путь/backup-identity.txt`. Храните приватный файл вне репозитория и вне каталога копий; ограничьте доступ владельцем. Получите публичного адресата: `age-keygen -y /защищённый/путь/backup-identity.txt`.
2. На машине резервного копирования задайте `BACKUP_AGE_RECIPIENT=age1...`. Для ротации задайте вместо него `BACKUP_AGE_RECIPIENTS_FILE` с одним публичным адресатом на строку. Приватный ключ на этой машине для создания копии не нужен.
3. Выберите `BACKUP_DIR` вне репозитория и с правами `0700`. Файлы копий получают `0600`. Если в старом каталоге уже лежат незашифрованные `.dump` или `.tar.gz`, перенесите их в отдельно защищённое место и разберите по утверждённому сроку хранения; новый скрипт их не удаляет.
4. Отдельно обеспечьте восстановление `LEARNER_DATA_ENCRYPTION_KEY`, `FRAUD_MATCH_KEY`, ключа сессий и конфигурации доступа. Не храните эти секреты рядом с копиями. Зашифрованная копия БД без ключа анкеты не восстановит защищённые поля.

## Создать пару копий

При работающих контейнерах Compose выполните с одной меткой:

```bash
BACKUP_DIR=/защищённый/каталог BACKUP_AGE_RECIPIENT=age1... scripts/db-backup.sh before-migration
BACKUP_DIR=/защищённый/каталог BACKUP_AGE_RECIPIENT=age1... scripts/attachments-backup.sh before-migration
```

Результат — `edu_crm-<UTC>-<метка>.dump.age` и `attachments-<UTC>-<метка>.tar.gz.age`. `DB_NAME` и `DB_USER` переопределяются для копии отдельной тестовой базы. Метка содержит только строчные латинские буквы, цифры и дефис. Неудачный `pg_dump`, `tar` или `age` оставляет без итогового файла; временный зашифрованный `.partial.*` удаляется. Скрипт не перезаписывает существующий итоговый файл.

## Ежедневная копия на рабочем Mac

`scripts/scheduled-backup.sh` берёт публичный адресат и каталог из закрытого `deploy/local/public-deploy.env`, создаёт сначала копию базы, затем вложений. Он запускается через LaunchAgent `deploy/launchd/tech.unicrm.backup.plist` ежедневно в 03:30 по местному времени, а при загрузке агента выполняет первый запуск. Для установки скопируйте plist в `~/Library/LaunchAgents/tech.unicrm.backup.plist` и зарегистрируйте командой `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/tech.unicrm.backup.plist`. Состояние: `launchctl print gui/$(id -u)/tech.unicrm.backup`. Логи: `~/Library/Logs/edu-crm-backup.*.log`.

Если в закрытом файле указан `BACKUP_AGE_IDENTITY_FILE`, новая пара расшифровывается этим ключом и проверяется как дамп PostgreSQL и архив tar. **Только после успешной проверки** удаляются полные ежедневные пары старше `BACKUP_RETENTION_DAYS` (по умолчанию 30 дней); всегда остаются как минимум `BACKUP_MIN_PAIRS` последних полных дней (по умолчанию 7). При отсутствующем или неверном ключе удаления не будет. Ручные копии перед выпуском, неполные пары и файлы с неизвестным именем не удаляются автоматически. Параметры задаются в том же закрытом файле конфигурации. Если Mac выключен или Docker недоступен, проверьте лог и выполните `scripts/scheduled-backup.sh` после восстановления работы машины.

## Отчёт о копиях и ручная копия из CRM

Каждый запуск `scheduled-backup.sh` записывает отчёт `status.json` (только имена, размеры и даты файлов, результат, этап ошибки, итог проверки) в `BACKUP_STATUS_DIR` — по умолчанию `deploy/local/backup-status` рабочей копии. Контейнер `api` видит этот каталог **только для чтения**; страница «Настройки → Резервное копирование» (только `crm-superadmin`) показывает отчёт.

Кнопка «Создать копию сейчас» создаёт флаг в `deploy/local/backup-requests`. Второй LaunchAgent `deploy/launchd/tech.unicrm.backup-request.plist` следит за этим каталогом и запускает `scripts/run-requested-backup.sh` — тот же скрипт копирования с меткой `manual-…`. Установка: `mkdir -m 700 deploy/local/backup-status deploy/local/backup-requests`, скопировать plist в `~/Library/LaunchAgents/`, `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/tech.unicrm.backup-request.plist`, пересоздать `api` (`docker compose up -d api`), затем один раз запустить `scripts/scheduled-backup.sh`, чтобы появился первый отчёт. Логи: `~/Library/Logs/edu-crm-backup-request.*.log`.

## Проверить восстановление

Перед восстановлением передайте `BACKUP_AGE_IDENTITY_FILE` как путь к приватному ключу. Скрипт сначала расшифровывает файл в поток `pg_restore --list`. Только после успешной проверки он создаёт **новую** базу. Существующую базу, в том числе рабочую, скрипт не заменяет. Если восстановление после создания новой базы не удастся, новая база удаляется.

```bash
BACKUP_AGE_IDENTITY_FILE=/защищённый/путь/backup-identity.txt \
  scripts/db-restore.sh /защищённый/каталог/<файл>.dump.age edu_crm_restore_check
BACKUP_AGE_IDENTITY_FILE=/защищённый/путь/backup-identity.txt \
  scripts/attachments-verify.sh /защищённый/каталог/<файл>.tar.gz.age
scripts/db-row-counts.sh edu_crm
```

Сравните количество строк рабочей и восстановленной базы. Для проверки самих вложений расшифруйте архив **потоком** в пустой временный каталог и сравните случайные имена файлов с `attachments.storage_key` восстановленной базы:

```bash
mkdir -m 700 /защищённый/временный-каталог
age -d -i /защищённый/путь/backup-identity.txt /защищённый/каталог/<файл>.tar.gz.age | \
  tar -C /защищённый/временный-каталог -xzf -
```

Проверочный каталог и базу удаляют по локальному регламенту после сверки. Рабочую базу не заменяют автоматически: после отдельного решения оператора приложение переключают на проверенную восстановленную базу.

## Ротация и срок хранения

Создайте новый приватный ключ, запишите старый и новый публичные адресаты в `BACKUP_AGE_RECIPIENTS_FILE`, затем создайте тестовую копию. Убедитесь, что **каждый** приватный ключ отдельно расшифровывает её и что база и вложения восстанавливаются. После этого оставьте в файле только новый адресат для следующих копий. Старый приватный ключ храните до истечения срока хранения всех копий, зашифрованных только на него. Удаление старого ключа раньше делает эти копии невосстановимыми. Срок хранения, доступ к каталогу и порядок удаления задаёт оператор под требования организации.

## Условие допуска реальных анкет

- [ ] Публичный адресат настроен; приватный ключ хранится отдельно и доступен уполномоченному оператору.
- [ ] Пара зашифрованных копий создана без открытых `.dump`/`.tar.gz`; каталог и файлы имеют ограниченные права.
- [ ] На вымышленных данных восстановлены новая база и вложения; количество строк и файлы сверены.
- [ ] Проверены доступ к копиям и секретам, срок хранения, процедура ротации и восстановление ключей анкеты и антифрода.
- [ ] Проверены права на полные анкеты и журнал действий; реальные файлы загружаются только после этих проверок.

Локальные автоматические проверки выполняет `bash scripts/tests/test-encrypted-backup.sh` с временными синтетическими данными и временными ключами. Они не обращаются к рабочей базе. Дополнительная репетиция с реальным PostgreSQL должна также использовать отдельную вымышленную базу.

26 сентября 2026 года выполнена `bash scripts/tests/test-encrypted-postgres.sh`: временный контейнер PostgreSQL без сети содержал только две вымышленные строки; новая база и тестовое вложение восстановились из зашифрованных копий. Контейнер и временные ключи удалены завершающим обработчиком скрипта. Это проверка механизма, а не разрешение загрузки реальных анкет: пункты готовности выше проверяются оператором для каждой рабочей среды.
