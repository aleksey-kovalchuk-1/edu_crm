# Резервное копирование и восстановление базы данных (разработка)

Git не хранит данные PostgreSQL. Перед миграциями схемы и рискованными операциями делайте резервную копию. Тома Docker (`postgres_data`) не удаляются — ни вручную, ни ради «чистого» старта.

Скрипты работают с запущенным контейнером `db` из `compose.yaml`.

## Создать копию

```bash
scripts/db-backup.sh before-migration
```

- Файл создаётся вне репозитория: `../edu-crm-backups/edu_crm-<время UTC>-<метка>.dump` (формат `pg_dump -Fc`).
- Метка — латиница в нижнем регистре, цифры и дефис.
- Архив проверяется `pg_restore --list` до переименования; незавершённый файл остаётся с суффиксом `.partial` и не считается копией.
- Переменные: `BACKUP_DIR`, `DB_NAME` (по умолчанию `edu_crm`), `DB_USER` (по умолчанию `crm`).

## Файлы вложений

Файлы, приложенные к сменам статусов, лежат в томе `attachments_data`, а их описание — в базе. Копируйте их вместе:

```bash
scripts/db-backup.sh before-migration
scripts/attachments-backup.sh before-migration
```

Архив `../edu-crm-backups/attachments-<время UTC>-<метка>.tar.gz` проверяется `tar -tzf` до переименования. Чтобы проверить копию, распакуйте её во временный каталог и сравните список файлов с колонкой `attachments.storage_key`.

Документы (T-093) — том `documents_data`, тем же способом:

```bash
scripts/documents-backup.sh before-migration
```

Архив `../edu-crm-backups/documents-<время UTC>-<метка>.tar.gz`; сравнивайте с колонкой `document_versions.storage_key` (только файлы в подкаталоге `documents/` — прошедшие проверку; `quarantine/` не содержит ничего долговременного).

Отчёты (T-050–T-052) — том `reports_data`, отдельного скрипта нет: файл отчёта — производный результат (тот же набор фильтров формируется заново `POST /api/v1/reports`), а не первичные данные, поэтому не входит в резервное копирование.

## Проверить или восстановить копию

Восстановление всегда выполняется в **новую** базу. Скрипт отказывается работать, если база с таким именем уже существует, поэтому рабочие данные не перезаписываются.

```bash
scripts/db-restore.sh ../edu-crm-backups/<файл>.dump edu_crm_restore_check
scripts/db-row-counts.sh edu_crm
```

Сравните количество строк в восстановленной и рабочей базах. Проверочную базу после сверки можно удалить:

```bash
docker compose exec -T db dropdb -U crm edu_crm_restore_check
```

## Вернуть данные в рабочую базу

Автоматического скрипта нет намеренно: замена рабочей базы — разрушительная операция. Порядок:

1. Сделать свежую копию текущего состояния: `scripts/db-backup.sh before-rollback`.
2. Восстановить нужную копию в новую базу и проверить её.
3. Остановить `api`, переключить `DATABASE_URL` на восстановленную базу, запустить `api`.
