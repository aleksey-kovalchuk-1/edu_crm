# API отправителей писем (T-102, email-infrastructure)

Модель и решения — D-210–D-213 в `docs/decisions.md`. Каталог отправителей полностью
администрируемый: создание/деактивация доступны только supervisor/admin, без отдельного
подтверждения владения адресом (D-211).

## Список отправителей

`GET /api/v1/email-senders` — доступен любой вошедшей роли. Возвращает только активных
отправителей.

`200` — `[{"id": 1, "email_address": "info@unicrm.tech", "display_name": "Общая почта", "is_active": true}, …]`.

## Добавить отправителя

`POST /api/v1/email-senders` — только supervisor/admin. `{"email_address": "info@unicrm.tech", "display_name": "Общая почта"}`.

`201` — `{"id", "email_address", "display_name", "is_active": true}`.

Ошибки: некорректный email или адрес уже используется активным отправителем — `422 VALIDATION_ERROR`
(`details[].field = "email_address"`). Если адрес ранее принадлежал деактивированному отправителю,
повторное добавление не создаёт дубликат и не ошибается — существующая запись реактивируется на
месте (тот же `id`, обновляются `display_name` и `created_by_user_id`) — D-213.

## Деактивировать отправителя

`DELETE /api/v1/email-senders/{id}` — только supervisor/admin. Мягкое удаление (`is_active = False`,
запись не удаляется физически) — `204`. Адрес пропадает из списка активных отправителей
(`GET /api/v1/email-senders`), но история событий и ссылки на запись из `users.email_sender_identity_id`
остаются валидными.

Ошибка: запись не найдена — `404 RECORD_NOT_FOUND`.

## Отправить тестовое письмо

`POST /api/v1/email-senders/test` — доступен любой вошедшей роли, без тела запроса. Письмо всегда
уходит на собственный email вызывающего из Keycloak (`auth.user.email`), никогда на адрес, переданный
клиентом, — иначе эндпоинт стал бы открытым инструментом проверки произвольного адреса (D-212).

`200` — `{"delivered": true | false, "message": "…"}`. `delivered: false`, если почтовый провайдер не
настроен (`EMAIL_PROVIDER_URL` не задан) — письмо только записывается в журнал сервера.

Ошибки: у вызывающего не указан email в профиле — `409 CONFLICT`; повторный запрос раньше чем через
минуту — `429 RATE_LIMITED` (`email_test_sent_at` на `users`, миграция 0016 — тот же принцип
охлаждения, что и у подтверждения телефона, D-156/D-157); сбой отправки — `503 SERVICE_UNAVAILABLE`
(таймстамп охлаждения не проставляется при неудаче, повторить можно сразу).

## Отправка писем

`backend/app/email.py`: без `EMAIL_PROVIDER_URL` (по умолчанию в локальной разработке и CI) письмо
пишется в лог контейнера API. Реальный провайдер подключается через
`EMAIL_PROVIDER_URL`/`EMAIL_PROVIDER_API_KEY`/`EMAIL_SENDER_ADDRESS`/`EMAIL_SENDER_NAME` в
`deploy/local/api.env` (не в репозитории). Формат запроса к `EMAIL_PROVIDER_URL` — предполагаемый
(реальной спецификации провайдера не было в наличии), как и у `app/sms.py` (D-157) — см. docstring
`app/email.py` и D-210: потребует уточнения под конкретного провайдера перед боевым использованием.
Поле `"from"` в теле запроса берётся из выбранного отправителя (`EmailSenderIdentity`, если он
назначен вызывающему) либо из `EMAIL_SENDER_ADDRESS` по умолчанию.
