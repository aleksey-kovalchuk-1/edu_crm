# API резервного копирования

Спецификация: `docs/superpowers/specs/2026-09-27-backup-settings-design.md`; решение D-230. Только `crm-superadmin`. API не работает с файлами копий: ни путей, ни выдачи файлов, ни восстановления, ни удаления.

- `GET /api/v1/backups/status` → `{"available", "reason", "last_run", "last_success_at", "stale", "pairs", "retention", "pending_request"}`. Источник — `status.json`, который пишет `scripts/scheduled-backup.sh` (через `scripts/backup_status.py`) и который смонтирован в API только для чтения (`BACKUP_STATUS_DIR`). `reason`: `not_configured` (каталоги не заданы), `no_report` (отчёта ещё нет), `damaged` (не читается или неизвестная схема). `last_run.result`: `running`, `success`, `failure` (`error` — этап: `preflight_failed`, `database_backup_failed`, `attachments_backup_failed`, `verification_failed`, `retention_failed`), `interrupted` (отчёт `running` старше 6 часов). `stale` — последняя успешная копия старше 36 часов или её нет. `pairs` — имена, размеры и даты файлов (до 60, новые сверху).
- `POST /api/v1/backups/manual` → `202 {"state": "requested"}`. Создаёт `request.json` в `BACKUP_REQUEST_DIR` (атомарно, `O_EXCL`); `409`, если запрос уже ждёт или копия выполняется; `503`, если не настроено. LaunchAgent `tech.unicrm.backup-request` запускает `scripts/run-requested-backup.sh`, который забирает флаг, игнорирует его содержимое и выполняет тот же `scheduled-backup.sh` с меткой `manual-YYYYMMDD-HHMMSS`. Ручные копии автоматически не удаляются. Событие журнала `backup.manual_requested`.
