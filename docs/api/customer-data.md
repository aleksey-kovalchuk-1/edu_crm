# Данные заказчика: API и импорт

## Доступ

Все маршруты требуют действующей CRM-сессии; изменяющие запросы требуют CSRF-токен. `crm-user`, `crm-supervisor` и `crm-admin` читают список компаний, контактов, краткий список слушателей и заявки. Создание, изменение, деактивация и импорт доступны только `crm-supervisor` и `crm-admin`. Полная анкета `GET /api/v1/learners/{id}` доступна только этим двум ролям; сервер возвращает `403` для обычного пользователя даже при известном ID. Поиск и краткий список слушателей не содержат СНИЛС, паспортных или дипломных номеров.

## Компании и контакты

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/v1/vendor-companies` | Список; `q`, `product_id`, `include_inactive` |
| `GET /api/v1/vendor-companies/{id}` | Карточка компании |
| `POST /api/v1/vendor-companies` | Создать, тело `{ "name": "…" }` |
| `PATCH /api/v1/vendor-companies/{id}` | Изменить `name` или `is_active` |
| `GET /api/v1/vendor-contacts` | Список; `q`, `company_id`, `product_id`, `include_inactive` |
| `GET /api/v1/vendor-contacts/{id}` | Карточка контакта |
| `POST /api/v1/vendor-contacts` | Создать: `company_id`, `full_name`, `phone`, `email`, `preferred_channels: string[]`, `product_ids: number[]` |
| `PATCH /api/v1/vendor-contacts/{id}` | Изменить поля контакта, продукты или `is_active` |

`product_ids` может содержать несколько продуктов, но все должны принадлежать компании контакта. `preferred_channels` — названия способов связи. «Чат в ТГ» не интерпретируется как Telegram-адрес. `GET /api/v1/it-products` дополнен `company_id` и `vendor_contacts`; прежние поля, в том числе текстовый `vendor`, сохранены. При переименовании компании текст `vendor` её продуктов обновляется, а их ID остаются прежними.

## Слушатели и заявки

`GET /api/v1/learners?q=…` возвращает только `id`, ФИО, телефон и email. `POST /api/v1/learners`, `PATCH /api/v1/learners/{id}` и защищённый `GET /api/v1/learners/{id}` работают с полной анкетой. Достаточно `last_name` и `first_name`; остальные поля необязательны. Телефон, СНИЛС, серия и номер документов, код подразделения и индекс передаются строками, чтобы сохранить ведущие нули.

Поля полной анкеты: `last_name`, `first_name`, `middle_name`, `phone`, `email`, `snils`, `passport_series`, `passport_number`, `passport_issued_by`, `passport_issued_at`, `passport_department_code`, `gender`, `birth_date`, `registration_region`, `registration_locality`, `registration_street`, `registration_house`, `registration_apartment`, `postal_code`, `dative_first_name`, `dative_last_name`, `dative_middle_name`, `education`, `diploma_profession`, `diploma_institution`, `diploma_last_name`, `diploma_number`, `diploma_series`, `diploma_registration_number`, `diploma_issued_at`. Даты имеют формат `YYYY-MM-DD`. СНИЛС и паспортные/дипломные идентификаторы шифруются отдельным ключом `LEARNER_DATA_ENCRYPTION_KEY`; без него запись этих полей не разрешена. Журнал действий содержит только ID записи и имена изменённых полей.

`GET /api/v1/course-applications` фильтруется по `course`, `stream_number`, `learner_id`; `GET /api/v1/course-applications/{id}` возвращает карточку. Поля: `external_number`, `course`, `stream_number`, `learner_id`, `learner_name`, `payment_status`, `payment_status_label`. Для данного источника допустим только `unconfirmed_by_data` / «Не подтверждено данными». Сумм, дат платежей и финансовых показателей эти маршруты не создают.

## Импорт: проверка и применение

`POST /api/v1/customer-imports/{kind}/preview` и `/apply` принимают `multipart/form-data` с `file` до 10 МБ. `kind`: `vendors` (`.xls`/`.xlsx`), `learners` (`.xls`/`.xlsx`) или `applications` (`.json`). При `/apply` можно передать `resolved_learner_ids` как JSON-объект `{ "номер_строки": learner_id }` для ручного выбора среди `candidate_ids` из предварительного отчёта. Применение повторно проверяет файл. Система не сохраняет исходные файлы, их строки или имя файла в истории импорта и аудите.

Для Excel можно передать `mapping` как JSON-объект `{ "поле_CRM": "Заголовок файла" }` на обоих этапах. Сервер проверяет существование и однозначность каждого столбца и наличие обязательных полей. Предварительный ответ показывает `template_version`, `mapping` и `unmapped_headers`; неизвестные непустые столбцы не загружаются автоматически. Шаблон без строк можно проверить, но применять нельзя. История доступна через `GET /api/v1/customer-imports/history` и `GET /api/v1/customer-imports/history/{id}` только руководителю и администратору. Она содержит счётчики и ссылки `row_number`, `entity_type`, `entity_id`, `action`, но не значения ячеек.

Отчёт содержит `summary` (`rows`, `valid`, `invalid`, `skipped`, `created`, `updated`) и `rows`: `row_number`, `status`, `action`, `errors`, `warnings`, `candidate_ids`. После применения добавляются `batch_id` и `record_links`. Неверные строки пропускаются; корректные применяются одной транзакцией. Диагностика не содержит значений документов. Неоднозначные контакты слушателей требуют ручного выбора; ФИО само по себе не служит ключом объединения. После выбора кандидата можно применить файл, даже если все строки до разрешения совпадений были отмечены как ошибки. Пустые ячейки повторного импорта не очищают заполненную анкету. Числовой телефон из Excel принимается только как целое из 11 цифр, начинающееся на `7` или `8`, с построчным предупреждением. Другие числовые телефоны, документы и индекс отклоняются.

### Колонки поставщиков

`Компания` → компания; `Продукт` → один или несколько продуктов (разделители `,`, `;`, перенос строки); `ФИО`, `Телефон`, `Почта` → контакт; `Способ связи` → список способов (те же разделители). Повторные строки сопоставляются по компании, продукту и имени контакта.

### Колонки слушателей

Все 30 заголовков переданного шаблона распознаны, включая объединённые подписи `Отчествопри наличии)`, `Имядательный падеж)`, `Фамилиядательный падеж)`, `Отчестводательный падеж)` и подписи `Номер телефона`, `Населенный пункт регистрации`, `Улица регистрации`, `Дом регистрации`, `Квартира регистрации`, `Учебное заведение по диплому`, `Фамилия, указанная в дипломе`. Обязательны фамилия, имя и хотя бы один контакт для надёжного повторного импорта. Пустой дополнительный столбец и вспомогательный лист не создают записей.

### JSON заявок

`Номер заявки` → уникальный `external_number`; `Курс` → `course`; `Номер потока` → `stream_number`; `Фамилия`, `Имя`, `Отчество`, `Телефон`, `Email` → данные слушателя для сопоставления. `null` пропускается с предупреждением. Телефон нормализуется до цифр с единым российским префиксом, email — регистронезависимо. Если email и телефон указывают на разных людей, отчёт показывает кандидатов для ручного выбора. Повторный внешний номер с теми же данными остаётся идемпотентным. При другом слушателе, курсе или потоке строка не меняет карточку и создаёт сигнал `application_number_conflict`.

## Антифрод и ручная проверка

`GET /api/v1/fraud-alerts` возвращает не более 100 сигналов за запрос с фильтрами `status`, `priority`, `limit`, `offset`; `GET /api/v1/fraud-alerts/{id}` возвращает один сигнал. `PATCH /api/v1/fraud-alerts/{id}` принимает `status`, безопасный `resolution_code` и обязательный `expected_updated_at`. Если сигнал изменился после открытия карточки, сервер возвращает `409`. Доступ к этим маршрутам имеют только `crm-supervisor` и `crm-admin`. Каждое решение попадает в неизменяемый журнал действий с кодом правила, статусом и причиной; значения документов, телефонов и почты в сигнале и журнале отсутствуют. Повторное обнаружение не открывает заново уже разобранный сигнал.

Версия правил — `1`. Сигналы `application_number_conflict`, `learner_match_conflict` и `document_identifier_reuse` имеют высокий приоритет. `shared_contact`, `batch_repetition` и `import_velocity` служат предупреждениями для проверки. Общий семейный телефон не объединяет разные анкеты автоматически. Порог `import_velocity` по умолчанию: более 500 строк в пакете или более 10 применений за час одним пользователем; значения задаются `FRAUD_BATCH_ROW_LIMIT` и `FRAUD_HOURLY_IMPORT_LIMIT`. Ни один сигнал не устанавливает статус мошенничества или оплаты.

Для сравнения СНИЛС и паспортной пары используется отдельный ключ `FRAUD_MATCH_KEY` (32 случайных байта в URL-safe Base64), версия `FRAUD_MATCH_KEY_VERSION` и HMAC-SHA-256. Исходные значения остаются зашифрованными ключом анкеты; в отпечатке и сигнале их нет. `GET /api/v1/fraud-alerts/status` показывает `disabled_no_key`, `needs_backfill` или `active`. Без ключа остальные правила и работа с анкетами продолжаются. Для старых анкет оператор запускает `python -m app.backfill_fraud_fingerprints` из backend с действующими `DATABASE_URL`, `LEARNER_DATA_ENCRYPTION_KEY`, `FRAUD_MATCH_KEY` и параметрами `--batch-size`/`--after-id`; команда выводит только количество и последний ID. После проверки полноты отпечатков оператор устанавливает `FRAUD_MATCH_COVERAGE_COMPLETE=true`. До этого сравнение документов не объявляется активным.

Ротация ключа требует окна обслуживания: выключить полноту покрытия, сменить ключ и увеличить версию, повторно построить отпечатки из зашифрованных анкет, проверить покрытие и лишь затем снова включить правило. Старую версию отпечатков и ключ убирают после успешной проверки и резервного копирования. Исходные файлы для калибровки порогов не используются.
