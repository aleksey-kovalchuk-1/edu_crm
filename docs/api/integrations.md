# API интеграций: мок LMS и мок CMS сайта (T-060)

**Это мок.** Реальные контракты LMS и CMS сайта заказчика не были предоставлены (D-008). Ниже — придуманный, но полноценно работающий и протестированный контракт для двусторонней интеграции; замена на настоящий контракт потребует переписать только слой разбора входящего JSON и формирования исходящего (`backend/app/connector_routes.py`), а не бизнес-логику CRM (`backend/app/connectors.py`, D-184).

Решения — D-184–D-187 в `docs/decisions.md`. Изменяющие запросы, как и весь остальной API, отвечают ошибками `{code, message, details}`.

## Авторизация

Не сессия Keycloak и не CSRF-токен (у внешней системы нет человека и браузера) — общий секрет в заголовке `X-Connector-Key`, один и тот же для обоих коннекторов (`CONNECTOR_API_KEY` в `deploy/local/api.env`, генерируется `scripts/generate-dev-secrets.sh`, не в git). Неверный, отсутствующий заголовок и незаданный ключ на сервере отвечают одинаково — `401 UNAUTHENTICATED` — так подбор ключа не может отличить одну причину от другой.

## Строка взаимодействия (`{connector}` — `lms` или `cms`)

Одна строка = одно взаимодействие (`Launch`) CRM. Идентичность между поставщиками — `(source, external_id)`: `source` — сам коннектор (`lms`/`cms`), `external_id` — идентификатор записи во внешней системе. Один и тот же `external_id` под `lms` и под `cms` — два независимых взаимодействия (это касается двух разных внешних систем, интеграция не пытается угадать, что они об одном и том же).

## Входящее сообщение (создать или обновить, идемпотентно)

`POST /api/v1/integrations/{connector}/interactions`

```json
{
  "external_id": "LMS-1001",
  "correlation_id": "c-abc123",
  "university": "Северный технологический университет",
  "program": "Python для начинающих",
  "product": "Учебная среда",
  "status": "Первый контакт",
  "responsible": "Иван Петров",
  "students": 25,
  "deadline": "2026-12-01"
}
```

Только `external_id` обязателен всегда. Остальные поля необязательны:

- **Если `(source, external_id)` встречается впервые** (создание) — `university`, `program`, `product`, `responsible`, `deadline` обязательны: без них — `422 VALIDATION_ERROR` с одной записью `details` на каждое отсутствующее поле. `university` ищется по точному названию (без учёта регистра) среди существующих вузов CRM; несуществующий — `422` (`field: "university"`). Новые вузы через интеграцию не создаются. `status` необязателен — по умолчанию первый активный статус базового процесса.
- **Если запись уже существует** (обновление) — переданы только те поля, которые нужно изменить; остальные не трогаются. `university` **не** используется при обновлении: интеграция не может задним числом перенести взаимодействие в другой вуз. `status`, если передан, ищется среди активных статусов процесса **этого** взаимодействия (не обязательно базового); несуществующий — `422` (`field: "status"`). Смена статуса добавляет в историю ту же запись (`status_changes`/`stage_events`), что и обычная смена статуса в интерфейсе.
- **Повторная идентичная доставка** — не создаёт вторую запись и не добавляет вторую запись в историю статусов: ответ `action: "unchanged"`, CRM-состояние не меняется.

Ответ `200`:

```json
{
  "crm_id": 42, "external_id": "LMS-1001", "source": "lms", "action": "created",
  "university": "Северный технологический университет", "program": "Python для начинающих",
  "product": "Учебная среда", "workflow": "Типовое взаимодействие с вузом", "status": "Первый контакт",
  "responsible": "Иван Петров", "students": 25, "deadline": "2026-12-01"
}
```

`action` — `created` / `updated` / `unchanged`.

## Исходящая выгрузка (текущее состояние в CRM)

- `GET /api/v1/integrations/{connector}/interactions?after_id=&limit=` — страница взаимодействий (по возрастанию `crm_id`, `limit` до 500), в том же формате, что и ответ на входящее сообщение; `external_id` — `null`, если это взаимодействие не связано с данным коннектором.
- `GET /api/v1/integrations/{connector}/interactions/{external_id}` — одно связанное взаимодействие; не найдено — `404 RECORD_NOT_FOUND`.

## Аудит и журналы

Каждое входящее сообщение — одна запись в журнале действий (`integration.{connector}.inbound`) с `source`, `external_id`, `action`, `launch_id`; без текста, без `responsible`/других персональных данных, без значения `X-Connector-Key`. Актёр (`user_id`) — `null`: коннектор действует от имени интеграции, не от имени пользователя CRM.

## Границы модели

`launches.product`/`launches.owner` — свободный текст без связи со справочниками ИТ-продуктов или пользователей CRM (D-180). Коннектор пишет туда как есть; сопоставление со справочником ИТ-продуктов для отчётов (`app/reports.py`) работает по совпадению названия, не по этому API.

## Изоляция адаптера

`backend/app/connectors.py` не знает про JSON, HTTP или конкретного коннектора — только про уже разрешённые сущности CRM (`University`, `WorkflowStatus`, `Launch`) и про идемпотентное создание/обновление. Разбор входящего JSON, поиск вуза/статуса по названию и формирование исходящего JSON — в `backend/app/connector_routes.py`. Замена мока на настоящий контракт LMS или CMS переписывает второй файл, не первый.
