| D-155 | Self-registration, email verification and password recovery are Keycloak's own hosted pages, reached through `GET /api/v1/auth/register?next=` (new, mirrors `/login`, builds Keycloak's `/protocol/openid-connect/registrations` URL instead of `/auth` via `OIDCClient.authorization_url(..., registration=True)`, same PKCE/state/browser-binding cookie); realm `verifyEmail: true` so an unverified account cannot complete the OIDC code exchange. | D-157 | Registration restricted server-side to `.ru` email addresses via Keycloak's Declarative User Profile `pattern` validator on the `email` attribute (`realm-edu-crm.json` → `components` → `org.keycloak.userprofile.UserProfileProvider`), not a frontend or backend check (backend never handles registration, D-002). `registrationEmailAsUsername: true` (one field, the one that's validated). `default-roles-edu-crm` gained `crm-user` as a composite so every new account starts with basic access; `crm-supervisor`/`crm-admin` stay manual (console or `scripts/keycloak-create-user.sh`). Two Keycloak 26.7.3 realm-import limitations found empirically and worked around with small idempotent post-boot Admin-REST-API jobs (same pattern as `keycloak-db-init`): (1) a `composites` list on a `roles[]` entry whose name matches the realm's already-autocreated default role is silently ignored by import — `deploy/keycloak/configure-default-role.py` adds `crm-user` afterward; (2) the demo accounts (`anna.demo`, `pavel.demo`, `irina.demo`), which already carry `default-roles-edu-crm`, therefore now also carry `crm-user` alongside their one elevated role — confirmed harmless: `sees_all()` in `backend/app/catalog_routes.py` checks for `crm-supervisor`/`crm-admin` membership, not the absence of `crm-user`, and a live login test shows the three accounts keep exactly `{elevated role, crm-user}` with no other stacking | D-007 (no real personal data — demo emails also moved to `@educrm-demo.ru`, see below); avoids a custom SPI (D-010) | ASSUMED |
| D-158 | Registration CAPTCHA: Keycloak's native `registration-recaptcha-action` (reCAPTCHA v2), set `REQUIRED` in a realm-import copy of the registration flow (`registration-with-recaptcha`) — no custom SPI, no Java toolchain needed (D-010). The execution's site/secret key cannot be set reliably by realm-import `${VAR}` substitution inside a nested flow on this Keycloak version, so a second idempotent post-boot job (`deploy/keycloak/configure-recaptcha.py`) PUTs them via the Admin REST API; local/CI default is Google's own published "always pass" test key pair, real keys go only in `deploy/local/keycloak.env` (never committed). A real, previously-unnoticed bug found and fixed in the process: Keycloak's default `Content-Security-Policy` (`frame-src 'self'`) silently blocks the reCAPTCHA iframe in every browser, not only a headless one — the realm now overrides `browserSecurityHeaders.contentSecurityPolicy` to allow `https://www.google.com` and `https://recaptcha.net` framing, verified by screenshot before/after. Login-side conditional CAPTCHA after N failures is *not* added: needs a custom authenticator SPI in this Keycloak version, out of proportion to the ask; `bruteForceProtected` (5-failure lockout, already in the realm) is treated as the login-abuse protection instead | Native support only; explicit login-side limitation documented rather than overclaimed | ASSUMED |

A real mailbox is set with `SMTP_HOST`/`SMTP_PORT`/`SMTP_FROM`/`SMTP_SSL`/`SMTP_STARTTLS`/`SMTP_AUTH`/`SMTP_USER`/`SMTP_PASSWORD` in `deploy/local/keycloak.env` only (gitignored, never fabricated) | Registration/verification work out of the box with zero configuration; matches D-129's local-secrets pattern | ASSUMED |
